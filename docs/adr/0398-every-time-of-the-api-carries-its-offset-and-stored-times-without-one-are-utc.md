# ADR-0398: Every time of the API carries its offset, a stored time without one is UTC, and the web UI shows times in the browser's time zone

## Context

The API answered its times in many forms: the naive `datetime.now()` of the supervisor's container (the audit log, backups, health, updates, the resource monitor and the stats), SQLite's naive `CURRENT_TIMESTAMP` and `datetime.utcnow()` from the DATETIME columns (users, API tokens, SMB passwords), btrfs's ctime ("Fri Nov  6 10:00:00 2026") for a scrub's start, openssl's "Nov  8 01:47:31 2027 GMT" for a certificate and seconds since the epoch for the host's boot. A browser reads a time without an offset as its own local time, so pages showed some times hours off (ledger entry `architecture.times-with-time-zones`, ADR-0023). The dev device's database keeps its rows: no table or column is altered and there is no migration framework (ADR-0319); the audit log's hash chain covers the text of its lines (ADR-0328). The decisions were delegated to the agent.

## Decision

- **What a stored time without an offset means: UTC.** SQLite's `CURRENT_TIMESTAMP` is UTC, every DATETIME column is written in UTC (`db_now()`), and the times that the supervisor wrote into its files of /data without an offset are the clock of its container, which runs in UTC (the `python:3.11-slim` image of `supervisor/Dockerfile`; `deploy/docker-compose.yml` sets no `TZ` and mounts no `/etc/localtime`). Nothing stored is rewritten: readers take such a time as UTC (also the times that a model keeps as text: the scheduler's runs and tasks, `last_run`, `schedule_since`, `started_at` and `finished_at`, from before ADR-0264, and a notification's `sent_at`, `UtcText`; a backup's manifest, whose `created` the restore answers; the SMART history and the RAID status). A history entry of a notification whose event `timestamp` is no time (POST /send took any text before) keeps its place without it.
- **`supervisor/src/times.py`** holds the rules: `utc_now()`; `db_now()`, UTC without a zone for a DATETIME column (SQLAlchemy's SQLite DATETIME drops a zone, so a column is given UTC only); `as_utc`, `parse_time`, `stored_time_text` and `with_offset`, which read a time without an offset as UTC (ValueError, so 422 or a line that is no entry, for a time outside the calendar in UTC); `utc_text`, a time in UTC with `Z`, as the models write it; `from_epoch` for an mtime or a boot time; `UtcText` for a time kept as text; and `UtcDatetime`, the type of every `datetime` field of a model, which validates a naive time as UTC and serializes any time, also one assigned after validation, in UTC with `Z`.
- **Answers.** Every point in time in an HTTP answer, a CSV or JSON export and a WebSocket message is ISO 8601 with its offset, in UTC: `Z` from a model, `+00:00` from `isoformat()`. The one exception keeps an offset too: a scheduled task's `next_run` is in the host's time zone (ADR-0266). Docker's times pass as Docker gives them (RFC 3339 with `Z`). Durations stay numbers. Changed forms: `boot_time` of `GET /system/info` is a time instead of seconds since the epoch (the step of ledger entry `system.boot-time-field` says so now); `last_boot` of `GET /power/status` is the current time less `/proc/uptime`, to the second, instead of `who -b`; a scrub's `last_run` is btrfs's ctime read as UTC (btrfs runs in the container), null for another form (`btrfs_time` in `supervisor/src/storage/pools.py`); a certificate's `valid_from` and `valid_until` are openssl's GMT dates (`openssl_time` in `supervisor/src/security/router.py`), null for another form; a notification event's `timestamp` is a time (422 for another value) and what a channel gets carries the offset. Names that carry a time (backup files, pre-restore copies, the ids of audit entries, tasks and firewall rules) are in UTC.
- **The audit log** keeps its lines as written: `AuditEntry.timestamp` is the line's text, so every hash still holds, and a line whose timestamp is no ISO 8601 time is no valid entry. New entries carry the time as the API answers it, in UTC with `Z` (`utc_text`), and so does the SMART history and the RAID status. The list and both exports answer `AuditEntryView`, whose `timestamp` is the entry's time in UTC with `Z`; the chain is judged over the lines' fields (`_chain_of`). The hash of an entry in the JSON export can be computed again from its fields: over the timestamp as given, or, for an entry recorded without an offset, the timestamp without its `Z`. Sorting, the filters, `/logs/summary` and `DELETE /logs` compare instants (`entry_time`), not text.
- **The rules of ADR-0237 that stay, with the bounds changed.** One dependency, `audit_filter` in `supervisor/src/audit/router.py`, gives `GET /logs`, `/logs/count` and `/logs/export` the same filters (`AuditFilter`): `action`, `username` and `severity` match exactly; `search` (at most 256 characters, without its surrounding spaces) matches any part, in any case, of the user, the action (also with spaces for its underscores), the client address, the browser, the resource as the page shows it and the details. A bound is `YYYY-MM-DD`, or that date, then `T` or a space, then `HH`, `HH:MM`, `HH:MM:SS` or `HH:MM:SS` with a fraction of 1 to 6 digits, and after a time optionally its offset, `Z` or `+HH:MM` (`_BOUND_FORM`); without an offset it is UTC. It covers its whole day, hour, minute, second or fraction. Any other value gets 422, and so does a `before_date` of `DELETE /logs` (an empty one removes nothing). The selection and its sorting run in the worker thread that reads the log (ADR-0224); `GET /logs` takes `limit` from 1 and `offset` from 0, `/logs/export` the `format` `json` or `csv`; other values, and a day or a time that does not exist, get 422. Both exports are downloads, `audit_log_<YYYYMMDD of UTC>.csv` or `.json`. The CSV export puts a `'` before each place where a spreadsheet would start a formula (`_spreadsheet_text`): a value that starts with `=`, `+`, `-`, `@`, a tab or a carriage return, and such a character after a semicolon, a tab or a line break inside a value. The list and the JSON export keep the other values as recorded. `/logs/summary`, `/actions` and `DELETE /logs` stay.
- **The web UI** reads a time of the API only with its offset and shows it in the browser's time zone, in the date format of `$intlLocale` (`webui/src/lib/time.ts`: `apiTime`, `formatDateTime`, `formatDate`, `formatTimeOfDay`, `localDay`); a value without an offset is shown as it comes, never as the browser's local time. Every page and component that writes a time of the server goes through it. The Audit Log page (`webui/src/routes/audit/+page.svelte`, for administrators only, in `ADMIN_ONLY_ROUTES` and the administrator's sidebar) shows the newest 100 matching entries as a timeline grouped by the browser's day, each with its time of day in the browser's zone; Show more loads them again with 100 more; an action is named by its value with spaces for its underscores; Search, User, Action, From and To apply 300 ms after their last change to the list and its count, and as they stand to Export CSV and Export JSON, which download through `downloadAs` under the server's file name with the browser's date; From and To are the browser's days, sent as their first and their last millisecond in UTC (`dayBound`). `webui/tests/roles.spec.ts` keeps a regular user off the page.
- **The rules of ADR-0300 that stay, with the start of a scrub changed.** The Storage page's texts come from `webui/src/lib/i18n/catalog/storage.ts`, its own words for a disk without a reason ("System disk", "In use") and the RAID levels offered for a new pool among them. A size it writes (of a disk, a partition, a pool, a filesystem found on the disks, a scrub's progress and rate) has one decimal in the number format of `$intlLocale`, without grouping, with the catalog's unit, by powers of 1024, written by the page's own code and not by the helpers of `webui/src/lib/stores/stats.ts`; a scrub's progress is a percentage with one decimal; the quota field still takes a number with a decimal point. A disk's in-use reason is the server's message and stays in English. A pool's RAID profile goes through a map from btrfs's profiles to keys, and a profile without a key is shown as it comes; lsblk's names, filesystem and partition-table types and `btrfs device stats -z` are shown as they come; a label shown on its own takes the language's quotes. `webui/tests/storage.spec.ts` ("The Storage page in Russian") shows the page and its dialogs in Russian. When the last scrub started is shown in the browser's time zone and the page's date format, in English too.
- **Tests**: `supervisor/tests/test_api_times.py` (no clock read without a zone in `supervisor/src`, every `datetime` field `UtcDatetime`, a walk of every GET of the API without a path parameter, and of those of `PATH_VALUES`, as an administrator in a process zone of UTC+05:45 with rows and files from before this decision, which fails for a time without an offset and for fewer than `MIN_ANSWERED` answers or a missing one of `MUST_HOLD_TIMES`; GETs that need the host, Docker or the network answer no 200 there, and their models are checked by type; the stats message, old rows and entries read back with their clock time in UTC, the audit chain across the change, bounds with offsets, the tools' times); `supervisor/tests/test_audit_log.py`; `webui/tests/times.spec.ts` (the answers that the pages read, and the Users page, in Asia/Kathmandu), `webui/tests/audit.spec.ts`, `webui/tests/storage.spec.ts`, `webui/tests/backup.spec.ts`, `webui/tests/language.spec.ts`, `webui/tests/api.spec.ts` and `webui/tests/api-tokens.spec.ts`.

## Consequences

- An API client gets every time with its offset, and a browser shows the same instant whatever zone the server, the host or the browser runs in. Two forms of the UTC offset, `Z` and `+00:00`, remain; both are ISO 8601. An offset in a query is written `%2B` for its `+`.
- A row or a line that the supervisor wrote before keeps its text; a time written without an offset in a zone other than UTC would be read wrong, and none is: the container has always run in UTC. A time written into a DATETIME column must be UTC, which the source check of `test_api_times.py` and `db_now` keep.
- A scrub start or a certificate date that btrfs or openssl prints in another form is answered as null, and the page shows none. A notification sent through the API with a `timestamp` that is no ISO 8601 time gets 422. An audit line whose timestamp is no time, or one outside the calendar in UTC, is skipped as damaged, and the chain breaks at the next entry.
- The Audit Log page's days and bounds are the browser's: two administrators in different zones see the same entries under different days.
- Not host-level; the device check after the next deploy reads `GET /api/v1/system/info`, `/auth/users`, `/auth/tokens`, `/security/login-history`, `/audit/logs?limit=5` and `/updates/history` (every time with its offset, the old rows with the same clock time as before), `GET /audit/logs` with every entry's `chain` "ok" across the first entries written after the deploy, and the Audit Log, Users and Storage pages in a browser outside UTC.

## Considered options

- Rewriting the stored rows and lines with an offset: it alters the data that ADR-0319 keeps, and every hash of the audit log written before would break.
- A SQLAlchemy type that converts every DATETIME on read and write: every comparison of the code with a naive time would change, for no gain while every write is UTC.
- One form of the UTC offset everywhere: the answers that already carried `+00:00` (the trash, the scheduler's runs as ADR-0266 states them, the notification history, the off-device copy) and their clients would change too.
- The audit log's new lines with `+00:00`: the JSON export, which answers `Z`, would no longer let a hash be computed again from it.
- The host's boot time as seconds since the epoch: unambiguous, but one rule, every point in time as ISO 8601 text, is simpler for clients and for the walk that checks it.
