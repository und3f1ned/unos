# ADR-0304: The scenario checks of the dev device are scripts that remove what they make and report each step's SD writes

## Context

A host-level change passes only after a check on the dev device and the same check after a reboot (ADR-0018). The checks of the slice 1 and slice 2 deploys, among them the SMB flows of ADR-0185 with a temporary account and share, ran from scratch scripts outside the repository, so the re-check after a reboot had nothing to run, and every agent had to write the flows again.

## Decision

- `scripts/dev/scenario.sh [--pool NAME] AREA...` runs the scenario check of each area, `files`, `volumes`, `smart`, `backups` or `smb` (`all`: every one), under the device lock (ADR-0210), and prints `SD writes scenario <area>` for each (ADR-0214), also for a check that a signal ended. The checks are in `scripts/dev/scenario.py`, which refuses to run without the lock of `scenario.sh` and whose `--help` lists the steps of each area; the feature-pass skill's table names the check of each host-level entry of `feature-list.json`.
- A check reads first how the device is (its baseline) and refuses to start beside names of an earlier check. It makes what it needs through the API (`scripts/dev/api.py`'s relay, ADR-0222, which now also uploads a file as a multipart form): users, shares, volumes and folders named `unoscheck` and the run's six hex digits, and backups, which get UNOS's own names. It prints PASS or FAIL for each step with the MiB written to the SD card meanwhile, and the first FAIL ends its steps. Then it removes what it made, newest first, also after a FAIL or an interruption (SIGINT, SIGTERM, SIGHUP), and compares the device with the baseline; a difference is a FAIL. While the clean-up runs, those signals are blocked, for it and the commands it starts; one that arrives then ends the run as interrupted once the clean-up is done. The session that holds the device lock ignores HUP and TERM, so a closed terminal or a TERM to the process group does not release the lock before the check ends (`dev_lock` of `scripts/dev/env.sh`). Each clean-up is registered before the call that makes its thing, and finds the thing by its name, so a call whose answer is lost is undone too; a backup whose answer was lost has no name the check knows, so the clean-up names the new backups and deletes none of them, since one made by hand meanwhile would look the same. Every call of the API or the device belongs to a step or to the clean-up, and a failure in either is a FAIL line. An output that can no longer be written (a closed terminal or pipe) ends the steps, since nobody reads them, and never the clean-up.
- Its commands on the device run through `scripts/dev/ssh.sh` in the read-only mount namespace (ADR-0221), with scratch files in `/dev/shm`, except `pdbedit`: tdbsam opens passdb.tdb read-write, which a read-only root refuses, so `pdbedit -L` and `pdbedit -P "password history"` run without it and only read. Subvolumes are made or deleted only below a check's own folder. The checks start no container (ADR-0183).
- The smb check runs smbclient on the device against 127.0.0.1, with a client configuration in a private folder in RAM that requires signing (`client signing` for a share, `client ipc signing` for the IPC$ of a share list) and keeps smbclient's own files there, and holds one session open while the API changes the share's access or the user's password (ADR-0103, ADR-0104); each such step names what Samba answered, its NT_STATUS or that smbclient ended. smbclient's standard input is unbuffered (`stdbuf -i0`), as it waits for a command with poll and then reads it with fgets. The anonymous attempt is a null session (`-N -U%`) without signing required by the client, so that only the server can refuse it; with a guest share, which admits null sessions (ADR-0098), it is not tried. The check signs in with one wrong password and with the password just replaced, the latter to show that Samba's password history spares passdb.tdb (ADR-0278).
- The temporary user's passwords and the backup's passphrase are made in the check's own process, reach the device only on standard input (the relay's request, an auth file of mode 600 in RAM that smbclient reads, and a file of mode 600 in RAM for the scan of the logs), are redacted in the output, and are looked for in the API's answers and, by the smb and backups checks, in the supervisor's log, the journal and the audit log (and Samba's log, by the smb check); a source that cannot be read is a FAIL.
- Running a scenario check changes the device for its duration: it runs when the owner asks for a check of the device (ADR-0016). The read-only checks of the device-checks skill stay as they are.
- Tests: `supervisor/tests/test_dev_scenarios.py` runs every area against a stand-in of the device in memory (the API, the host and a Samba that keeps a tree connect's access until close-share and ends an account's sessions at a password change): each passes and leaves the stand-in as it was; a 500 at any API call of a step, before or after the call changed something, an interruption, an output that fails or a refusal of the device still removes everything; a failed clean-up and leftovers are reported; the defects each check exists for fail it; every call is a route of the supervisor with a body its model accepts; and the SMB helper's session and share-list protocol works against a stand-in smbclient. `supervisor/tests/test_dev_scripts.py` covers the relay's upload.

## Consequences

- The re-check after the owner's reboot is `scripts/dev/scenario.sh all` plus the checks by hand that the table lists. Each scenario check removes what it makes, so its run after a reboot shows that the scenarios work after the reboot, not that something made before it is still there; where an entry's steps ask for that, its notes give the steps by hand. A check that is repeated by hand becomes a step or an area of `scripts/dev/scenario.py`.
- The stand-in of the tests only knows what the checks ask, and the contract test only checks the requests; a difference from the real device shows at the first run there, as a FAIL with the API's answer, Samba's NT_STATUS or the device's error.
- A run that loses its connection cannot clean up: the next run names the leftovers and refuses to start, and removing them is a step by hand (the device-checks skill); leftover backups are named only by the run that made them.
- The checks write to the SD card, and each step's line shows how much: the API's database and audit log at every change (and about 0.02 MiB of container logs per API call, ADR-0222), smb.conf at every share change, `/etc/passwd`, `/etc/shadow` and their backup copies when the account is made and deleted, passdb.tdb when the account is made, its password changed, a wrong password tried (ADR-0159) and the account deleted, two backups of the database on the data volume, which the backups check deletes again, and a `sync` with each measurement.
- The files check's first Delete makes the pool's trash folder where it had none; UNOS keeps it, empty and hidden, as after any Delete.
- Not checked by these scripts, and listed in the feature-pass skill's table: a restore of a backup, a supervisor restart, a pool mounted read-only, a bind mount below a folder, guest shares, Empty trash, scrubs, the Scheduler's tasks and what survives a reboot.
