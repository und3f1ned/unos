# ADR-0418: An iSCSI target serves a sparse file of a volume through the kernel's LIO with mandatory CHAP, and UNOS restores its targets at every start

## Context

`shares.iscsi-targets` asks for an iSCSI target that an administrator makes from a volume, with one LUN and CHAP, that several initiators may use and that refuses an initiator without the credentials. The Linux kernel's target (LIO) is configured through configfs, whose state lives in RAM and is gone after a reboot; the dev device has its modules `target_core_mod` and `iscsi_target_mod` but no targetcli, and, as its check of 2026-11-19 found, no backstore: its vendor kernel builds none of FILEIO, IBLOCK, PSCSI and USER, so it has no `target_core_file` and serves no target. The owner asked "above all that it be safe" (ADR-0013): a LUN holds a whole file system of another computer, and its secrets give access to it.

## Decision

The host and its kernel:

- LIO through the host's configfs (`/sys/kernel/config/target`), driven by `supervisor/src/shares/iscsi.py` through `src/host.py` (ADR-0020): no host package. targetcli-fb is a front end of the same files, and its own saved configuration and restore service would be a second record of the state beside UNOS's database. The modules are loaded with the host's `modprobe -a target_core_mod target_core_file iscsi_target_mod` (`modprobe` joins `HOST_TOOLS` with the package kmod), and configfs is mounted when systemd did not mount it.
- Host scripts, run with `/bin/sh` and checked under sh and dash by `supervisor/tests/test_iscsi_scripts.py`: one prints the state of UNOS's targets and storage objects in configfs, with the initiators that have a session; one checks the LUN files before they are served (below); one makes a LUN file and one deletes it; one loads the modules; and one applies a list of operations that Python computed (make or remove a folder, write an attribute, make or remove a link) read from its standard input, each path checked to lie below `/sys/kernel/config/target/` without `..`. A value is written with the shell's builtin `printf`, so a CHAP secret is on no command line, and an error names the operation and the path, never the value. Every other value (names, IQNs, addresses, paths, sizes) is checked in Python before it reaches a script (ADR-0293).
- What belongs to UNOS in configfs: the targets whose IQN starts with `iqn.2003-01.org.linux-iscsi.unos:` and the storage objects of the HBA `core/fileio_3260`. UNOS changes nothing else there: targets made by hand stay.

A target (`iscsi_targets` and `iscsi_initiators` in the database, `supervisor/src/shares/models.py`):

- A name of 1 to 32 lowercase letters, digits and `-`, starting with a letter or digit, and the IQN `iqn.2003-01.org.linux-iscsi.unos:<name>.<8 hex digits>`, the digits random per target: two NAS devices with a target of the same name never give initiators one IQN on two portals, which they would take for two paths of one disk.
- One LUN, LUN 0: a sparse file `<volume>/.unos-iscsi/<name>.lun` of the size given in whole GiB (1 to 65536), made with `truncate` in a new file (the shell's noclobber: an existing file is never overwritten or resized), owner root and mode 0600, in the folder `.unos-iscsi` of the volume's top folder, owner root and mode 0700 (`chmod 00700` after `mkdir`: a folder made in a setgid folder, an SMB share's, inherits the bit), which UNOS keeps immutable (`chattr +i`) while it holds a LUN: neither an SMB user who can write in the volume's top folder, nor the Files page, nor a container can rename, replace or delete the folder or the files in it, while LIO still writes into the files. The scripts that make, check and delete the files work from inside the folder, entered with `cd -P` and checked with `pwd -P` to be the folder of that name in the volume, so that a rename in the volume's top folder while the folder is not immutable cannot point them elsewhere. The size must fit in the volume when the target is made: in the free space that `df` gives for the volume, and below the volume's quota less what it uses. The space is not reserved; the tab says so.
- The file keeps btrfs's data copy-on-write and checksums (no `nodatacow`): a scrub of a RAID1 pool repairs a damaged block of the LUN as it repairs any file (ADR-0011), and snapshots of the volume stay consistent; the cost is fragmentation under random writes. LIO's fileio backstore writes through (`O_DSYNC`, without `fd_buffered_io` and with `emulate_write_cache` 0), so an acknowledged write is on the pool's disks; UNMAP is on (`emulate_tpu`, `emulate_tpws`), so that an initiator's discards free the pool's space. The storage object's name and its VPD unit serial are the target's random id, so an initiator sees the same disk after every restore.
- CHAP is mandatory, one-way at least: the target portal group has `attrib/authentication` 1, `generate_node_acls` 0, `demo_mode_write_protect` 1, `cache_dynamic_acls` 0 and `param/AuthMethod` CHAP, so that only the allowed initiators log in and only with CHAP. Each allowed initiator (1 to 16, `iqn.`, `eui.` or `naa.` names in lowercase) gets an ACL with the target's CHAP user name and secret, and LUN 0 mapped read-write. Mutual CHAP is an option: a second secret that the target answers with, which must differ from the first (RFC 7143). A user name has 1 to 64 letters, digits, `.`, `-`, `_`, `:` and `@` (the target's name by default); a secret 12 to 16 characters of letters, digits and `!#%+,-./:=?@^_~` (12 to 16 is what the Windows initiator accepts), generated by UNOS (16 letters and digits, from `secrets`) unless the administrator types one; neither starts with `NULL`, which LIO takes for none. A new secret, and mutual CHAP turned on or off, make the target's ACLs anew, which ends their sessions: an initiator logged in with a leaked secret does not stay in. Discovery (SendTargets) needs no CHAP: it names the targets and their portals, never a LUN.
- The secrets are stored as the off-device copy's are (ADR-0337): in `/data/iscsi_secrets.json`, mode 0600, replaced whole and synced, keyed by the target's random id; neither in the database nor in the configuration backups. The answer to a create, and to a change that sets a new secret, holds the secret once; no other answer, log line, audit entry or command line holds one. A target without its secret (a database restored from another installation, a secrets file kept as `.bad`, ADR-0324) is not served, and the tab says to set a new secret.
- Portals: TCP 3260 on each address of the local networks (`shares.listen.is_lan_address`: the networks of ADR-0095, not the loopback or IPv6 link-local) of the host's enabled, broadcast-capable interfaces other than Docker's (`network.links.is_hidden`), not one that is still tentative or failed duplicate address detection: not on every address, not on a point-to-point tunnel. Read with `ip -j addr show` at every apply; a check every 5 minutes, only while a target is served, applies again when the addresses changed (one host command that reads; no write and no log line otherwise, ADR-0214). UNOS's firewall rules (ADR-0416) gain TCP 3260 from each local network, with the comment `UNOS: iSCSI`, added at an Enable and a Reset as the others are.

Its lifecycle:

- The supervisor's start applies the database's targets in the background (the lifespan of `supervisor/src/main.py`), and so do a restore of the database and a mount of a pool that holds a target's LUN: each target whose pool is mounted, whose LUN file is in place with its size and whose secret is stored is served, missing parts of it made, and UNOS's targets and storage objects that the database no longer has are removed; an apply that finds configfs as it should be writes nothing. A target that cannot be served is left out of configfs, and the tab names why; one whose volume cannot be checked now (btrfs fails or does not answer) is left as it is, sessions included. Each target's operations run apart: one that the kernel refuses (an address taken on 3260, a file it cannot open) is removed again, so that no ACL stays without its CHAP values, and named, and the others are served. An unserved target is not retried by the 5-minute check, whose apply would ask btrfs about the pools and wake their disks (ADR-0378).
- Every change (create, change, delete) applies the whole state the same way, under one lock. Changes: the allowed initiators, a new CHAP secret, mutual CHAP on or off or a new secret of it. The size, the volume and the name do not change. A create that the kernel does not serve is taken back whole (rows, secret, LUN file); a change that it does not take is kept and answered with its new secrets, never to be shown again, and the target says why it is not served.
- Delete removes the target from configfs (its sessions end), then the LUN file, the row and the secret. It always needs the target's name typed again (`confirm`, 400 otherwise), as other irreversible storage operations do (ADR-0035), and the dialog says which initiators are logged in; a target whose pool is not mounted is not deleted (409), so no row goes while its file stays.
- A pool whose volume holds a target's LUN is not unmounted or forgotten, and such a volume is not deleted (409, naming the target), checked under the lock of `supervisor/src/storage/pools.py` with which a create makes the file; the target is deleted first.
- Every route is the administrators' (ADR-0030), under `/api/v1/shares/iscsi` (the area `shares` of API tokens, ADR-0392); where host commands run locally (`UNOS_HOST_EXEC=local`: the stand-in, the test stack) every route answers 503 and runs nothing, as the firewall's do (ADR-0416). The audit log gets `iscsi_target_created`, `iscsi_target_changed` and `iscsi_target_deleted`, with the name, IQN, volume, size, initiators and CHAP user, and "a new CHAP secret" for a new secret.
- The web UI: an iSCSI tab of the Shares page (`webui/src/lib/components/shares/IscsiTab.svelte`).
- Tests: `supervisor/tests/test_iscsi.py` (the API and the apply against a fake host and a fake configfs), `supervisor/tests/test_iscsi_scripts.py`, `supervisor/tests/test_firewall.py`, `webui/tests/iscsi.spec.ts`.

## Consequences

- LIO's state follows the database at each start and change: a target made by hand with UNOS's IQN prefix or in its HBA is removed.
- A LUN's space is thin: a pool that fills up makes the initiator's writes fail. With snapshots of the volume, data that an initiator rewrites takes space again.
- A new address of the host is served within 5 minutes; until then initiators that use it are refused.
- An SMB share of a volume with a LUN lists a folder `.unos-iscsi` that its users cannot open, and Repair permissions cannot change it.
- Nothing ends LIO's targets when the host shuts down: the kernel holds the LUN files open, so systemd cannot unmount the pool or make it read-only, and the host powers off with the pool mounted, after its last sync; btrfs mounts it cleanly again. Ending the targets when the supervisor stops would end every session at each restart of the supervisor, while the kernel serves them on without it; a unit of the host that ends them at shutdown is left for later.
- UNOS's rule for 3260 is added when the firewall is turned on or reset: a firewall that was on before has it only after one of those (UNOS has no older installations, ADR-0207).
- The device check of the entry is by hand (the feature-pass skill), with open-iscsi on the device as the test initiator; the stand-in's E2E specs answer the tab's requests with route fakes.
- A host whose kernel lacks one of LIO's modules (`target_core_mod`, `target_core_file`, `iscsi_target_mod`) is told so by GET (`kernel_support` false), and a create there answers 409 before anything is made.

## Considered options

- `nodatacow` for the LUN file: no fragmentation and space that `fallocate` really reserves, but no checksums, so a RAID1 scrub could not tell the good copy of a LUN's block; data integrity came first.
- A block backstore over a loop device of the file: one more host device per target to keep and restore, for nothing that fileio lacks.
- Portals on every address (`0.0.0.0:3260`): they would follow address changes at once, but answer on Docker's bridges and on tunnels too.
- targetcli-fb from `deploy/install.sh`: a host package, and a second saved state with a restore service of its own.
