# ADR-0406: An installed app updates to the catalog's newer pinned images with a copy of its database, and can be rolled back

## Context

Until now an app was updated by an uninstall and an install of a newer catalog after a snapshot of the pool (ADR-0381): Immich migrates its database at its server's start and refuses a downgrade, so the earlier image digests alone cannot take it back, and Docker's data root is on the dev device's SD card, where every pull writes (ADR-0214). The ledger entry `apps.update-in-place` asks that an installed app update in place to the catalog's newer pinned images, keep its data folders, generated secrets and settings, copy its database before the new version migrates it, show what it writes to the system disk before it runs, run as a background job that reports over `/ws/v1/events`, and roll back to the earlier digests and that copy. The owner delegated the choices, asking above all that it be safe.

## Decision

- **What is installed and what the catalog pins.** A container's own record is the truth: Docker's `Config.Image` (`name@sha256:<index digest>` for a pinned image, ADR-0381), its image (`Image`: the digest of the image's configuration in the graph driver's store, of its index in the containerd image store; the image's `Created` and `RootFS.Layers`) and its bind mounts. Every container an install or update makes also carries the label `unos.app.version` (the template's `version`); one made before it has none and shows no version. `InstalledApp.update_to` is the catalog's version when every image of the template, its hardware profiles' included, is pinned and the catalog pins for one of the app's containers another index digest than the one it was created from (its own or a profile's: which one this host takes is the update's to read); it reads nothing but the containers' configuration (`stacks.update_to`). An app of a floating tag (`UNPINNED_TEMPLATES`, transmission among them) is never offered an update: GET and the job answer 409 "<name>'s image floats on a tag (...): UNOS updates only an app whose catalog pins its images by digest".
- **What "newer" means.** For each container whose pin differs, the update reads the catalog's image for the host's platform from its registry (`supervisor/src/apps/registry.py`): the index of the pinned digest, the platform's image manifest (its layers and their compressed sizes) and the image's configuration (`created`, `rootfs.diff_ids`), anonymously, over HTTPS only, each answer checked against the digest it was asked by, a blob redirected to a CDN fetched without the token. A container whose image is the one that runs (the same configuration digest, or the same layers and build time, as the containerd store names images by their index) keeps its image. Each other image must be newer: its `created` later than Docker's `Created` of the image that runs; earlier, equal or unknown answers 409 ("UNOS does not move an app to an older image", "cannot tell whether"), which also stops a supervisor rolled back to an older catalog from downgrading an app. An index without the host's platform answers 409, and the recorded platforms of ADR-0403 are checked before (`_check_platform`, with the hardware profiles' images); a registry that cannot be read answers 503 "...; nothing was changed".
- **What it writes to the system disk.** Docker's data root and the containerd image store are on the system disk. A layer is there when its chain id (the digest of the layer with all those below it, by which the graph driver and containerd's snapshotter keep unpacked layers) is among those of the images in Docker's store (`client.images.list()`, `RootFS.Layers`); for each image to pull the missing layers' compressed bytes are the download, and the image's `PinnedImage.disk_bytes` times the missing share of its compressed bytes is what it writes (three times the download for an image without a record). `GET /api/v1/apps/installed/{id}/update` answers `AppUpdatePlan`: each container's image before and after (and when each was built), `download_bytes`, `system_disk_bytes` and the system disk's free space now, and the database copies; the App Store shows it in its update dialog before Update now. The job refuses (409) when the system disk would keep less than ADR-0381's 2 GiB.
- **What is kept.** The update recreates every container from the catalog's current template with what the installed app has: each pool folder at the source that its container binds now at the same path (its install's choice of pool and overrides), a folder that the new template adds on the app's pool (`unos.app.pool`), the password files bound as they are and never made again (a missing one is 409, ADR-0381), the values of the template's editable variables from the main container's environment (never PUID or PGID), the group option unos-smb when its PGID is 70000 (a new version that cannot run in the group is refused), its host ports from `PortBindings` (a port the new template adds is checked against other containers and the host), the limits in force in each container's HostConfig (ADR-0390) and the hardware profiles that apply on this host now (ADR-0382). A request that the old values cannot meet (a new required variable) is a 409 that asks for an uninstall and an install, which keep the data. The app's network is used again.
- **The copy of the database.** `VolumeMapping.copy_before_update` marks a folder of an app's own data that a newer version may migrate beyond the earlier one's reach: Immich's `{pool}/apps/immich/postgres/data`. After the pulls and after the app's containers were stopped in reverse order with their stop timeouts (the database's 60 s, a clean shutdown), the update copies it with `cp -a --reflink=auto` (`host.run_in_container`, at most 3600 s, ADR-0290) to `<folder>.copying` beside it on the same pool, renamed to `<folder>.previous` when complete; on btrfs the reflink copy shares the blocks until they differ. Never on the system disk: it is a sibling of the folder, on its pool. The plan refuses when that pool has less free than the folder's size plus 1 GiB (the new version may rewrite every block), when the folder is no real folder reached without links, and when a `.previous` or `.rolled-back` folder of an earlier update is there ("move it away first, since UNOS replaces no copy of a database"). A `.copying` folder is UNOS's own unfinished copy and is deleted before a new one.
- **The update job.** `POST /api/v1/apps/installed/{id}/update` answers 202 with a job of `src/apps/install_jobs.py` (`AppInstallJob.kind` "update"): the same slot as the installs of ADR-0384, so one install, update or rollback runs at a time on the NAS, holding the app's lock (no start, stop, uninstall or limits meanwhile), its states in RAM and sent to administrators in the `app_installs` message of `/ws/v1/events`. Its steps: `checking` (everything of the plan again), `pulling` (by digest, with ADR-0384's progress; an image Docker has is `present`), `stopping`, `copying`, `creating` (the earlier containers renamed `<name>.previous`, then the new ones created by ADR-0381's code with the same names), `starting` (the companions of `depends_on` ready, then the main container healthy, or running without a health check, within 900 s; an unhealthy state does not fail it before then, since Immich fails its health check while it migrates). Nothing changes before the stop: a cancel or a refusal up to then ends the job with the app as it was ("Cancelled by <user> before <app> was stopped: nothing was changed").
- **A failure in the middle.** From the stop on, a failure, a cancel or an unexpected error restores the app (`step` `restoring`): the new containers (those of the app's key that are not earlier ones) are stopped and removed, the copy is put back in the folder's place once a new container may have touched it (the folder as the new version left it is `<folder>.rolled-back` until the earlier containers have their names back, then deleted; when the copy's own rename fails, the folder's is undone) or deleted when none could have, an unfinished `.copying` is deleted, the earlier containers get their names back and start in order if the app ran before the update. The job ends failed (or cancelled) with the reason and "<app> was returned to its earlier version". When a new container cannot be removed or a copy cannot be put back, the earlier containers keep their `.previous` names and stay stopped (they would start on data that a newer version may have migrated), and the message says so: the Installed tab offers the rollback, which tries again. A stop of the supervisor during these steps leaves everything as it is (503, as an install's, ADR-0384) and names it; the Installed tab then offers the rollback.
- **The earlier version, and the rollback.** After a successful update the earlier containers stay, stopped, as `<name>.previous`, with their configuration and images, and the copy as `<folder>.previous`; every template restarts `unless-stopped`, so Docker leaves them stopped at a boot (a test holds every template to that policy). They are the app's (`unos.app` label, `InstalledContainers.previous`, `InstalledApp.previous`), none of its containers for a start, a stop or the listing's fields; another update waits until they are gone (409). An earlier container binds the folders that the newer version uses, so the Containers page refuses to start or restart one (409 from `prepare_app_start`), and it starts, restarts or removes a container of an app only while no install, update, rollback or other change of that app holds the app's lock (409). `POST /api/v1/apps/installed/{id}/rollback` (202, a job of kind "rollback", which cannot be cancelled: 409) checks that each copy and its folder are there and no `.rolled-back` folder is, stops any earlier container that runs and the newer containers, removes the newer ones (those created after every earlier one: an earlier container that an interrupted update did not rename keeps its name and is started with the others), moves the newer database aside, puts the copy in its place, gives the earlier containers their names back, starts them in order and waits for the main container as the update does; then it deletes the newer database. What the app stored after the update is lost, which the App Store's question says. `DELETE /api/v1/apps/installed/{id}/previous` removes the earlier containers and deletes the copy (the images stay for Containers > Images), and refuses while the folder is missing or a `.rolled-back` folder is there, when the copy may be the only database; an uninstall removes the earlier containers too and keeps the copy, like every data folder. Copies and folders are renamed and deleted relative to a descriptor of their parent opened without following links (`open_dir_nofollow`, `shutil.rmtree` with `dir_fd`, ADR-0042); cp gets the folder's path right after a walk that found no link on it, below folders of root that no container binds.
- **Platforms (ADR-0403).** The update pulls only images recorded for the host's platform and that its registry's index names for it; an app that is not available here is refused before any read of a registry.
- **Audit.** `AuditAction` gains `app_updated` (the versions, each changed image from and to, the copy and the earlier containers kept; success false with what it did when it failed after the stop, was cancelled then or stopped by a stop of the supervisor), `app_rolled_back` and `app_earlier_version_removed`; an uninstall's `app_uninstalled` names the earlier containers it removed. A refusal before anything changed writes nothing.
- **Roles.** The four routes are for administrators only (`supervisor/src/apps/updates.py`'s router is in `_ADMIN_ONLY` of `supervisor/src/main.py`, and each route requires an administrator, ADR-0030); a regular user gets 403.
- **Tests.** `supervisor/tests/test_app_updates.py` against the strict fake Docker of `supervisor/tests/docker_fake.py` (now with images' `Created` and `RootFS`, `images.list`, a container's `rename`, scripts by image and a start hook) and a fake registry transport; `test_apps.py`, `test_app_stacks.py`, `test_app_install_jobs.py` and `test_ws_auth.py` for the new label and job field; `webui/tests/apps-update.spec.ts` on the stand-in with route fakes and the fake events socket, and the update dialog in `webui/tests/mobile-layout.spec.ts`. The device check is by hand, from the ledger entry's notes.

## Consequences

- An update of Immich writes only the layers that changed to the SD card, and the copy of its database costs no space on a btrfs pool until the new version rewrites it; the earlier containers keep the earlier images on the SD card until the earlier version is removed and the images are removed on Containers > Images.
- Only apps whose catalog pins its images update in place; the others still need an uninstall and an install (`apps.pinned-catalog-images` pins them).
- The update reads the image registries from the supervisor, which needs the network then, as the pulls do.
- Only folders that the catalog marks are copied: Immich's library, and the data of an app without a marked folder, stay as the newer version left them after a rollback.
- A stop of the supervisor or a power cut during an update or a rollback can leave the containers under their earlier names, which the Installed tab and the Containers page show; Uninstall removes them all and keeps the data.
- A copy left by an interrupted update, or after an uninstall, blocks the next update until it is moved away.
- The rollback finds the copies through the current catalog's `copy_before_update` marks: a template change that drops a mark while an earlier version is kept must be reviewed with that in mind.
- An image whose build time is fixed (an epoch, for reproducible builds) is never taken as newer: such an app cannot be updated in place.

## Considered options

- Comparing the catalog's `version` with a label: containers installed before the label have none, and a version string does not order Postgres's tags; the build time of the image for this platform does.
- Recreating the earlier version at a rollback from recorded digests and the current template: the template is the new version's; the kept containers are Docker's exact record of the earlier one.
- `pg_dump` into the pool instead of a copy of the stopped folder: a dump needs the database running and a restore into an empty database with the earlier image, more steps that can fail; a copy of a cleanly stopped folder is complete and, on btrfs, free until it differs.
- Recording each pinned image's layers in the repository instead of reading the registries: the record needs the network whenever a pin changes, and could not be made for the pins of today without it.
