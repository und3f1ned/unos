# ADR-0384: An app's install runs as a background job whose progress the App Store shows

## Context

Superseded by ADR-0437: only in part, what an install's card shows while it downloads: how many images are on the NAS and one bar of the whole download in which each image is an equal share, without the layers; every other rule here stays in force.

ADR-0381 kept the install of an app one request that answered after its pulls: Immich's four images took 299 s on the dev device, during which the App Store showed only a spinner, a browser could give up on the request, and nothing said how far the pulls had come. The ledger entry `apps.install-progress` asks that `POST /api/v1/apps/install` answer at once with a job, that the checks, pulls, creates and starts run in the background, and that the App Store show each image's pull, each container's start and the result, also after a reload. The owner delegated the choices, asking above all that it be safe. This ADR supersedes only the part of ADR-0381 that made the install one request and named `scripts/dev/api.py --timeout 3600` for it; every other rule of ADR-0381 (the model, the identity, the password on the pool, the pinned images, the checks before the first pull and their order, the readiness waits, the clean-up of a failed install, the system disk, Immich) stays in force as written there. It also replaces ADR-0254's statement that the pull of an app's install has no deadline, for that pull alone: the Images tab's pull keeps ADR-0254's rule, which stays in force otherwise.

## Decision

- **The request.** `POST /api/v1/apps/install` answers 202 at once with the job (`AppInstallJob` of `supervisor/src/apps/schemas.py`), running, at the step `checking`. Before it starts the job it answers only what reads neither Docker, the host nor the pools: 422 for a body it does not take, 404 for an app that the catalog lacks, 400 for a request that the template refuses (the group option, a host port outside 1 to 65535, given twice or moved in the host's network, a variable that UNOS sets, a missing or placeholder value: `_check_request` of `supervisor/src/apps/router.py`), and 409 while an install runs or another change of the app is under way. Every other check of ADR-0381 (the pool, the folders and the share folders, the password files, the app's names and network in Docker, the host ports in use, the system disk's free space, the hardware) runs in the job, in ADR-0381's order and before any pull; a refusal ends the job `failed` with the detail and the HTTP status that the request answered before (`error`, `error_status`). The App Store keeps its details dialog open while the job checks, so that such a refusal still shows where the request was made.
- **One install at a time.** A second install while one runs, of the same app or of another, answers 409 ("Immich is being installed already: wait for the end of its install", "An install of Immich is under way: install Jellyfin once it has ended") and starts nothing. The checks of the free space and of the ports hold only against what is there before the pulls: two installs at once would each pass them against the same free space and the same ports. The job holds the app's lock (`stacks.acquire`, the lock of `stacks.app_lock`) from the request to its end, so that a start, stop, restart or uninstall of the app answers 409 meanwhile.
- **The job runs in a thread of its own** (`supervisor/src/apps/install_jobs.py`): a daemon thread, not the event loop and not its executor, which a pull of minutes would hold (ADR-0254, ADR-0021). The check of the slot, the app's lock and the new job are taken in one hold of the module's lock, and a job that cannot be made or started frees them again; at its end the thread frees the app's lock and the slot before it publishes the end, whatever ended it, and a state of a job that a newer job of the app replaced meanwhile is dropped. A job that failed writes one warning to the supervisor's log, since its request answered 202.
- **Its state is kept in RAM only.** `install_jobs` keeps the running job and the last job of each app since the supervisor started, by the app's id: a new install of an app replaces its last job, and `DELETE /api/v1/apps/install/jobs/{id}` (204) forgets an ended one, as the App Store's Dismiss does (404 for one that is not kept, which the App Store takes as done: another tab dismissed it); on the running job it is a cancel (below). Every new state of a job is a new object in memory; no progress is written anywhere, so the system disk (the dev device's SD card, ADR-0214) gets only what the install itself writes: the images, the container records, the pool's folders and password file, and one audit entry.
- **What it reports.** `step`: `checking`, `pulling`, `creating` (the pool's folders, the network, the containers), `starting`, `cleaning` (the removal of what a failed or cancelled install made). `images`: each image once, in the order of the containers that run it, listed once the checks passed: `waiting`, `present` (a pinned image that Docker has, not pulled), `pulling`, `pulled` or `failed`, with `layers` (the layers that Docker's pull stream named so far), `layers_done` ("Pull complete" or "Already exists"), `bytes_total` (the download sizes of the layers that Docker reported so far) and `bytes_done`. `containers`: each container in its start order, `waiting`, `created`, `starting` (for a companion of `depends_on`, until it is ready), `running`, or, after a failure, `failed` (the one whose create, start or readiness failed) and `removed` (by the clean-up). The end: `succeeded` with `result`, the `AppInstallResponse` that the request answered before, `failed` with `error` and `error_status`, or `cancelled` with `error`, what the cancel did; `finished_at` in each case.
- **The pull stream** (`supervisor/src/apps/pulls.py`). The install sends Docker's `POST /images/create` through the session of docker-py's client (`client.api.post` to `{base_url}/v{api_version}/images/create`, without credentials: the catalog's images are public) and reads the stream of JSON lines to its end in the job's thread, each line into the job's counts, as docker-py's own `pull` reads it; a line with an error, a line that is not JSON and Docker's refusal before the stream fail the pull, which answers ADR-0381's "Failed to pull image ...". Unlike docker-py's `pull`, which sends no timeout, the read waits at most `PULL_STALL_SECONDS` (600 s) for each line, requests' read timeout: Docker sends a line for each step of each layer, and a pull that sends nothing for 10 minutes has stalled, which fails it with "Docker sent nothing about it for 10 minutes, so the pull was stopped; install the app again to try once more" instead of holding the one install until the supervisor restarts. The whole pull has no deadline: a large image on a slow link takes as long as it takes. The job keeps the pull's response, so that a cancel or a stop of the supervisor ends a read that blocks at once (`pulls.abort`: urllib3's shutdown of the socket), and Docker ends a pull whose client went away. The counts are published at most once a second (`PROGRESS_INTERVAL_SECONDS`), a change of state at once. A pinned image is still pulled by its digest and tagged afterwards (ADR-0381).
- **How the App Store learns it.** `/ws/v1/events` sends administrators `{"type": "app_installs", "data": [...]}`, the jobs as `GET /api/v1/apps/install/jobs` answers them, after `auth_ok` once there is a job and whenever they change, at most every 2 seconds like its other messages (`supervisor/src/websocket/events.py`); regular users never get it. The web UI keeps them in the store `appInstalls` (`webui/src/lib/stores/appInstalls.ts`), which `auth_ok` empties, so that after a restart of the supervisor, which forgot its jobs, no install shows as running. A reload of the App Store signs in to the socket again and gets the jobs back: the running install with its progress, and the result of the last ones. The App Store shows a card per job above its tabs (`webui/src/lib/components/apps/AppInstallJobs.svelte`): each image's state, its layers and a bar of its bytes, each container's state, and the end, the install's notices, the failure or the cancel, with Cancel install while it runs (after a question) and Dismiss once it ended. It reads the installed apps again when a job ends, and when a job it saw running is gone from a new socket's list: a supervisor that restarted forgot it, and its containers may be there. The details dialog that waits for the checks asks for its job once (`GET`) when the events socket signs in again, and a 404 says that UNOS restarted during the install and its progress was lost. Nothing polls (ADR-0365).
- **For scripts.** `GET /api/v1/apps/install/jobs` lists the jobs, and `GET /api/v1/apps/install/jobs/{id}?wait=SECONDS` (0 to 3600) answers the job once it has ended or the seconds have passed, looking at it in memory every half second without holding a thread or a database session (it closes the one that checked the credentials first, so that no read transaction holds back the database's checkpoints, ADR-0306). Each waiting GET holds a connection, which counts against uvicorn's `--limit-concurrency 128` (ADR-0333): at most `MAX_WAITERS` (4) wait at once, and another answers 429 "Too many requests wait for install jobs; try again in a moment". A device check waits for an install with `scripts/dev/api.py POST /apps/install -` (202 with the job's `id`), then `scripts/dev/api.py --timeout 3660 GET /apps/install/jobs/<id> --param wait=3600`, which replaces ADR-0381's `--timeout 3600 POST`.
- **Cancel.** `DELETE /api/v1/apps/install/jobs/{id}` on the running job answers 202 with the job as it is and asks it to stop as the administrator's cancel (`install_jobs.cancel`): the install stops at its next check (below), and a pull's read that blocks ends at once. Before any container or network is made, the job ends `cancelled` with "Cancelled by <administrator> before any container of <app> was made". Once it made one, everything it made is removed as after a failure (ADR-0381's clean-up: each container it started stopped with its stop timeout, then all removed in reverse order with the network, the folders, password files and images kept, and a database folder that was empty before named as maybe half set up), at the step `cleaning`, and the job ends `cancelled` with the clean-up's message; a clean-up that cannot remove everything is audited as after a failure. A cancel that comes while the install fails anyway ends it `cancelled`, with the failure's message. The App Store's Cancel install asks first, since the cancel removes what the install made.
- **A stop of the supervisor** asks the running job to stop, ends a pull's read that blocks, and waits up to 5 seconds for the job's end (`install_jobs.stop_for_shutdown`, beside the repair's stop in the lifespan of `supervisor/src/main.py`, both at once). Uvicorn waits for the open requests before it runs the lifespan's shutdown, and a GET that waits for a job's end can stay open for an hour, so both images and the stand-in run uvicorn with `--timeout-graceful-shutdown 3` (`supervisor/Dockerfile`, `supervisor/Dockerfile.test`, `scripts/standin/run_supervisor.py`): the requests still open 3 s after the SIGTERM are ended, and the shutdown's 5 s of waits fit in Docker's 10 s before it kills the container (`deploy/docker-compose.yml` sets no `stop_grace_period`). The install looks for a stop or a cancel at each line of a pull, before it writes to the pool, before the network and each create and start, and at each look while it waits for a companion (`stacks.wait_ready`'s `check`). Before any container is made, the job ends `failed` with 503 and nothing in Docker: the images pulled so far stay, and so do the folders and the password file if they were made, as after any failure of ADR-0381. Once it made a container or the network, it leaves what it made as it is, not stopped and not removed, since a forced removal would kill a database halfway through its first start, and writes `app_installed` with success false naming what was left behind; its message names a database folder that was empty before and may be half set up, as ADR-0381's clean-up does, and when only the network was made it says so: the next install uses that network again. The restarted supervisor knows no job: the app is then listed as installed, stopped or incomplete, and its Start (with ADR-0381's waits) or Uninstall goes on from there. A kill or a power cut leaves the same without an audit entry; a pull cut off with the supervisor's connection ends in Docker.
- **The audit log** keeps ADR-0350's rule and ADR-0381's texts: one `app_installed` per job, written by the job's thread before its end is published, with the administrator and the client of the request: success when it installed, success false when the clean-up of a failure or a stop of the supervisor left something behind, and nothing when its checks refused it or its clean-up removed everything. Starting a job, cancelling one and dismissing one are not audited: none of them changes the NAS by itself (a cancel's clean-up that leaves something is audited, as above).
- **Roles.** The install, the cancel and the job routes are for administrators only (the apps router is in `_ADMIN_ONLY` of `supervisor/src/main.py`, and each route requires an administrator, ADR-0030), and so is the socket's message: a job names an app's folders on the pools.
- **Tests.** `supervisor/tests/test_app_install_jobs.py` (the 202 at once, the answers before the job, one install at a time, the app's lock, the pull's layers and bytes, the containers' states and steps, the end and its audit entry, a refusal of the checks, an error in a pull's stream, a pull that stalls, a failed start and its clean-up step, the listing, dismissing, waiting and the bound on waiters, a cancel before any container, during a pull that blocks and after a container was made, a stop of the supervisor before and after a container was made, after the network alone and during a pull that blocks, the job's own bookkeeping, and under a real uvicorn a stop that a waiting GET does not hold back and that stops the install, the roles), `supervisor/tests/test_request_limits.py` (both images bound uvicorn's graceful shutdown alike, within Docker's 10 s), `supervisor/tests/test_ws_auth.py` (`TestTheInstallsOnTheEventsSocket`); the install tests of `test_apps.py`, `test_app_stacks.py` and `test_audit_storage_and_apps.py` read the job's end through `install` of `test_apps.py`, against the pull stream of `supervisor/tests/docker_fake.py`; `webui/tests/apps-install-progress.spec.ts` on the stand-in, with the jobs on a fake events socket (`fakeInstallEvents` of `webui/tests/apps-fakes.ts`; its `restart` is a supervisor that forgot its jobs), and the job API of the stand-in itself in `webui/tests/api.spec.ts`.

## Consequences

- A user can leave the App Store, or reload it, while Immich downloads, and sees how far each image has come; a browser no longer waits minutes for one request.
- A refusal that only the checks find (a port in use, too little space, a share's folder) comes a moment after the click, from the job, instead of in the answer; the dialog still shows it.
- Only one app installs at a time. A stalled pull ends the install after 10 minutes without a line, and an administrator can cancel any install at once; a pull that keeps sending lines without end (a registry that trickles) still holds the slot until it is cancelled.
- A restart during an install can leave an app installed but not started, or incomplete; the Installed tab shows it, and Start or Uninstall handles it. The App Store does not show the last result of an install across a restart.
- Scripts and device checks that installed with one request and `--timeout 3600` now need the waiting GET.
- A GET that still waits 3 s after the SIGTERM is cancelled by uvicorn: its client gets 500, and the supervisor's log an "Exception in ASGI application" error with the CancelledError, which `scripts/dev/check.sh` lists for a day (seen on the dev device on 2026-11-17). The web UI never waits that way: it learns the end from the events socket.

## Considered options

- Keeping the cheap checks of the pool, the ports and the free space in the request, with their 4xx: they read the host and Docker, which can take seconds or 60 s when Docker hangs (ADR-0254), against "answers at once"; the dialog that waits for the checks keeps their messages where they were.
- Installs of several apps at once, with checks that count the pulls of the other jobs: more code for the rare case of two installs, while one at a time keeps the space and port checks true.
- Keeping the jobs in the database, to show them after a restart: a write per state on the SD card for a result that the Installed tab and the audit log already give.
- Rolling back what an install made when the supervisor stops: the database's stop timeout (60 s) does not fit in Docker's 10 s, and a removal cut off halfway would leave less than the stop does. A cancel has no such limit, so it rolls back.
- Ending a waiting GET from the job's stop event at a stop of the supervisor: uvicorn waits for the open requests before the lifespan sets that event, so only a bound on uvicorn's graceful shutdown reaches it.
- A watchdog thread per pull instead of requests' read timeout: the read timeout bounds the silence of the stream with no thread, and the kept response serves the cancel.
- A page that polls `GET /apps/install/jobs/{id}`: ruled out by ADR-0365; the events socket already reaches every administrator's page.
