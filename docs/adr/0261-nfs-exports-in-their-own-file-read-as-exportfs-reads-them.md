# ADR-0261: UNOS keeps its NFS exports in its own export file on the host, reads every export file as exportfs reads it, and applies them with the host's exportfs

## Context

`supervisor/src/shares/nfs.py` wrote the supervisor container's own `/etc/exports`, which no bind mount shares with the host: a file on the container's writable layer on the system disk, lost when the container is recreated. It ran `exportfs` in the container, which has none, and its parser kept only the first client of each line, so a delete rewrote the file without comments, other clients and the lines it misread (`shares.nfs-exports`, `shares.nfs-exports-parser`). ADR-0163 had left the parser for later, and ADR-0175 lists it for review. Where a web export may point and to whom is ADR-0262.

## Decision

- exportfs reads the main export file and then every `*.exports` file of the directory beside it whose name does not start with a dot, each on its own: an entry that it cannot read ends the reading of that file, and of no other. UNOS writes only its own file in that directory, `/etc/exports.d/unos.exports` (`nfs.py`: the directory is `settings.nfs_exports_path` plus `.d`). It starts it with two lines of comment; an add appends one line, a delete removes the line of that export, and every other line, in it and in every other file, stays byte for byte, its newline included. A line of UNOS's is one exactly as UNOS writes it (ADR-0262), alone on its line: the folder, one address or network in the form UNOS writes it, `ro` or `rw` and the fixed options with `mp=` of the folder's pool. A line written by hand into UNOS's file, also one that differs from that form by a byte or holds a second entry, is the owner's, as the file's first lines say. UNOS never writes `/etc/exports`.
- `supervisor/src/shares/exports.py` reads an export file as nfs-utils 2.8 does, ported from `support/nfs/xio.c` and from `getexportent` and `parseopts` of `support/nfs/exports.c`: continuation lines, comments, quotes, `\ooo` escapes, several clients on a line, `-` default options, `(options)` and lines without clients for everyone, and the option list with the checks of its values. An entry that exportfs cannot read is a problem with its file and line; the entries after it in that file are not listed, since exportfs never reads them. The files of the directory are listed by name, where exportfs orders them by version, which changes only the order of the list.
- `GET /api/v1/shares/nfs` lists every entry of every file: the path, each client with its options and its access (the last of `ro` and `rw`; none when `sec=` gives each flavor its own), the file and line, and `managed` for a line of UNOS's. `GET /api/v1/shares/nfs-status` names as problems the entries that exportfs cannot read and the exports of UNOS below a folder that other accounts can change (ADR-0262), and says whether the host lacks exportfs (`server_missing`). Only an export of UNOS can be deleted: any other entry, in another file or written by hand into UNOS's, answers 409 with its file and line, for the owner to change on the NAS. While any export file has an entry that exportfs cannot read, an add and a delete are refused (409, naming the file and line): the `exportfs -ra` that applies a change would read no further in that file and stop exporting what follows the entry, the owner's exports too, and a new line of UNOS's file after it would never be read.
- One host command lists the files and prints their bytes in hex (`od`), so that no byte changes on the way, CR included; UNOS's file is written with `write_host_file_atomic` with the same bytes for every line it keeps (`mkdir -p` and a sync of `/etc` before the first one), through `supervisor/src/host.py` (ADR-0020). An add is refused (409) when the file ends inside an entry, with a backslash at the end of its last line or an open quote, which would take the new line in. The check of the folder and the write hold the lock of `supervisor/src/storage/pools.py`, which its check of a volume's users holds too. After a change `timeout --kill-after=5 60 exportfs -ra` applies every file on the host (ADR-0258). What exportfs reports is a warning of the change, never its failure: it exits with status 1 for a problem in any file, also in a line UNOS did not write. Status 127 names the missing NFS server and its package. `exportfs -ra` makes the host's exports those of the files, as the NFS server does at every start: an export made with `exportfs` on the command line, which no file holds, ends. `exportfs` is in `OPTIONAL_HOST_TOOLS` of `host.py`, with `nfs-kernel-server`: `deploy/install.sh` does not install it, so the startup check of the host's programs (`HOST_TOOLS`, ADR-0020) leaves it out, and the NFS tab says when it is missing. A change is audited as `share_created` or `share_deleted` with the resource type `nfs_export` (ADR-0157).
- `deploy/uninstall.sh` removes UNOS's export file and runs `exportfs -ra`, so that the host stops exporting those folders.
- The steps of `shares.nfs-exports` name UNOS's file instead of `/etc/exports`, and the first step of `shares.nfs-exports-parser` names `exports.py`.
- Tests: `supervisor/tests/test_nfs.py`, `supervisor/tests/test_volumes.py` (an export of a volume in any file blocks its deletion), `supervisor/tests/test_deploy_scripts.py` (the uninstallation), `supervisor/tests/test_lifespan.py` (the startup check leaves exportfs out), `webui/tests/nfs-exports.spec.ts`.

## Consequences

- A mistake in `/etc/exports` no longer stops exportfs from reading UNOS's exports, and a line in UNOS's file cannot stop the owner's. While a file has an entry that exportfs cannot read, UNOS adds and deletes no export, so that its change never ends a live export: the owner corrects the line first, which the NFS tab names.
- An export made with `exportfs` on the command line ends at UNOS's next change, as it does at the NFS server's next start.
- A line of UNOS's that the owner changes on the NAS out of the form UNOS writes is the owner's from then on: UNOS lists it with its file and line, and no longer deletes it.
- `deploy/install.sh` does not install the NFS server. With `nfs-kernel-server`, rpcbind and nfsd listen on every address of the host, also on hosts that export nothing, and the dev device filters nothing (ADR-0227): whether the install installs and enables it is the owner's call. Until then the NFS tab says to install the package, and the host's NFS server applies the exports when it starts, also at every boot.
- An exportfs older than nfs-utils 2.8 may refuse an option that 2.8 knows; the rules that span several entries (duplicates, `reexport=` with `fsid=`) stay exportfs's own.
- A listing runs one host command; the volume check of `supervisor/src/storage/pools.py` reads the exports the same way.

## Considered options

- UNOS's lines in `/etc/exports`, marked with a comment as `supervisor/src/storage/pools.py` marks its fstab lines: UNOS would rewrite the owner's file, and a line of the owner's that exportfs cannot read would stop it from reading every UNOS line after it.
- Exports rendered from the database, as smb.conf is: a table and an import of the existing exports, for lines that UNOS alone adds and removes.
- Every entry of UNOS's file deletable, also those written by hand: the file's first lines and the steps of `shares.nfs-exports-parser` promise that UNOS keeps every line it did not write.
- Applying only UNOS's entry (`exportfs -i -o <options> <client>:<path>` on an add, `exportfs -u <client>:<path>` on a delete), which would keep the exports after an unreadable entry and those made on the command line: how `-u` matches the client that exportfs keeps in its table, and what `-o` does to an entry that a file also holds, could not be checked against a real exportfs in this change, while the refusal needs only the reader of the files.
