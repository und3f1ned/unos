# ADR-0378: Data disks get an idle timeout that UNOS keeps in a udev rule, and nothing UNOS does periodically wakes a sleeping disk

## Context

`storage.disk-spindown` asks for an idle timeout per data disk, refused for the system disk, and a Storage page that shows whether each disk sleeps while reading SMART data does not wake it. Disk Health woke every disk (`smartctl` without `-n standby`, ADR-0235), and so did the RAID monitor every 5 minutes for a disk that no mounted pool holds open: `btrfs filesystem show` reads the superblock of every block device through libblkid. The owner's words for this batch (in translation): "then we continue developing UNOS's features with our test hardware in mind", under the standing delegation "work on through the features, ask no questions; I allow everything" (as ADR-0340). The dev device's only data disk is the pool's 640 GB SATA hard disk `sda` behind a JMicron AHCI controller (ADR-0376), and its host has hdparm (installed by the owner for this entry).

## Decision

- **Values.** Off or 5, 10, 20, 30 minutes, 1, 2, 3, 4 or 5 hours (`SPINDOWN_MINUTES` of `supervisor/src/storage/schemas.py`): what `hdparm -S` expresses (5-second steps to 20 minutes, `-S 1` to `240`; 30-minute steps from 30 minutes to 5.5 hours, `241` to `251`), from 5 minutes, below which a disk of a quiet NAS spins down between the bursts of one session and wears with each start, to whole hours. `hdparm_value` and `minutes_of` of `supervisor/src/storage/spindown.py` convert.
- **Setting.** `PUT /api/v1/storage/disks/{name}/spindown` with `{"minutes": n}` (administrators, ADR-0030; 422 for a value not offered) runs `hdparm -S <value> /dev/<disk>` on the host under `timeout` (ADR-0020, ADR-0258) and then writes UNOS's udev rule `/etc/udev/rules.d/90-unos-disk-spindown.rules` (`write_host_file_atomic`), one line per disk: `ACTION=="add", SUBSYSTEM=="block", ENV{DEVTYPE}=="disk", ENV{ID_SERIAL_SHORT}=="<serial>", RUN+="/sbin/hdparm -S <value> $devnode"`, then `udevadm control --reload` (a failure is logged: udevd sees a changed rules folder by itself). The file is written only when a disk's line or its record (below) changes, removed when neither is left (ADR-0214), and keeps only UNOS's lines. The answer is `{"name", "minutes", "warning"}`, `warning` null unless the disk's own scans could not be switched (below). A change is audited as `settings_changed` of the resource `disk` (ADR-0351); hdparm's failure answers 500 and keeps nothing; a rule that cannot be written after hdparm set the timeout answers 500, saying the disk has it until it restarts, and is audited as failed (ADR-0350).
- **Kept in the udev rule, not in a table or the supervisor.** udev runs the line whenever the disk appears, at boot before the supervisor starts and when it is plugged in again under any name, matched by the serial; the supervisor would need a watcher for new disks and would send `hdparm -S`, whose IDLE command spins a sleeping disk up, at each of its own starts. The rule is the setting's only home, as a pool's fstab entry is its mount's (ADR-0283): GET /storage/disks reads it back (`spindown`), and no table can disagree with what the host does. Debian's `/etc/hdparm.conf` is left to the owner: it is the host's own file.
- **The disk's own automatic offline scans are off while it has a timeout.** Measured on the dev device's `sda` on 2026-11-16, with smartd off, no read or write counted in `/proc/diskstats` in any test, and no smartctl, hdparm, udisks or similar process on the host (watched every second for 25 minutes): in the morning `hdparm -S 60` and `-S 120` put it in standby after 660 s, and the device check passed (standby after 660 s for 300 s); after a reboot at 07:17 it stayed active for hours with the `-S 240` of UNOS's rule (run at boot and again by `udevadm trigger`: udev's debug log shows `/sbin/hdparm -S 240 /dev/sda` ran and succeeded), with `-S 240` set by hand (35 minutes, read every 5 minutes), `-S 180` (27 minutes) and even `-S 120` (18 minutes). `smartctl -c` then said "Offline data collection status: (0x84) Offline data collection activity was suspended by an interrupting command from host. Auto Offline Data Collection: Enabled.", a total time to complete offline data collection of 14760 seconds, and the capabilities 0x7b, among them "Suspend Offline collection upon new command" and "Auto Offline data collection on/off support"; `/etc/smartd.conf` has only `DEVICESCAN -d removable -n standby -m root -M exec ...`, without `-o on`, so the collection was the drive's own setting. After `smartctl -o off` (the status then 0x05, "aborted by an interrupting command from host") and `hdparm -S 120` it slept after 661 s; the drive was then restored (`smartctl -o on`, `hdparm -S 240`). So a drive's automatic offline data collection (SMART subcommand DBh, which smartmontools' `ataprint.cpp` names "Enable/Disable Auto Offline (SFF)" after SFF-8035i; `smartctl -o on`: a surface scan every 4 hours that runs for hours, suspended by any command of the host and resumed later) keeps the disk out of standby, and a timeout of UNOS's does not work on such a disk for most of the time. Therefore `spindown.set_timeout`, after `hdparm -S` (whose IDLE woke the disk, so these reads wake nothing), reads it with `smartctl -n standby -i -c -j <disk>` in the container (`host.run_in_container`, at most `SMARTCTL_TIMEOUT`, 30 seconds, ADR-0290): bit 7 of `ata_smart_data.offline_data_collection.status.value` is on, bit 1 of `ata_smart_data.capabilities.values[0]` the disk's switch for it (`isSupportAutomaticTimer`, smartmontools' `ataprint.cpp`); `-i`, which reads the identity that `-c` reads anyway, adds `smart_support`, whose `available` or `enabled` false marks an ATA disk without SMART or with SMART turned off, which runs no such collection (a SMART timer function, which SMART DISABLE OPERATIONS stops; `-c` alone says "SMART Disabled" only as text, which `-j` drops). For a timeout, a collection that is on is turned off with `smartctl -n standby -o off -i -c -j <disk>` (smartctl reads the SMART data again after `-o`, so its JSON shows the state it left, which must be off), and the rule gets the comment line `# UNOS turned off the automatic offline data collection of the disk with the serial <serial>` after the disk's line (`spindown.RECORD`; `read_rule` keeps it, `render` writes it, a record edited by hand is dropped as an edited line is; one whose disk has no line, its line edited by hand, stays until that disk's Off). Another timeout keeps the record (and turns the collection off again if something turned it on). Off (0) turns it on again with `-o on` only for a disk that the rule records, and removes the record. A collection that was off already, or a disk without one (no switch for it; an NVMe disk, which gets no timeout; a SCSI or SAS disk, for which smartctl reads no ATA SMART data and whose `-o` smartctl does not send: `smartctl.cpp` sets it in the ATA options alone; an ATA disk without SMART or with SMART off), is left as it is and not recorded. A failure (smartctl does not answer the first read or reads no state, the disk has no switch for a collection that is on, or it is still on after `-o off`) does not fail the Save: the timeout is set, the failure is logged, the answer's `warning` says "<disk> has the idle timeout, but the disk's own automatic offline scans could not be turned off (<reason>): they may keep it awake" (`SCANS_LEFT_ON`), the Storage page shows it above the disks, and nothing is recorded. An `-o off` without a clear answer (smartctl killed at its timeout, or no state read after it) is recorded all the same, since smartctl sends the command before it reads the SMART data again (`ataprint.cpp`) and the drive may have taken it: the record only makes Off send `-o on`, which puts back the state UNOS found, while a missing record would leave the collection off for good; the warning then says "<disk> has the idle timeout, but whether the disk's own automatic offline scans were turned off is unknown (<reason>): they may keep it awake" (`SCANS_MAYBE_ON`). A failed `-o on` at Off keeps the record ("... could not be turned on again (<reason>): save Off again to try once more", `SCANS_LEFT_OFF`). When the rule cannot be written, the collection is put back as the old rule, which stays, records it: on again when the change added the record (the drive would keep it off with no record), off again when it removed it (the old rule sets the timeout again at boot, which the scans would keep from working); what could not be put back is added to the 500 answer's reason. The change is audited with the timeout's ("... and turned off its automatic offline data collection"). The drive keeps the setting itself, across power cycles: that is assumed, not confirmed. The command is SFF-8035i's, not one that the ATA/ACS standards define as far as could be checked here (smartmontools' `ataprint.cpp` says that only IBM documents the status bit), so the drive's own documentation decides, and it is not confirmed for the dev device's disk either, which has not been power-cycled with it off; the device check's first step fails when the rule records the collection off but the drive has it on, which a run after a reboot (ADR-0018) shows. Only the Save turns it off: no periodic command, and nothing at boot.
- **Refused with the reason** (`spindown.problem`, also as `spindown_problem` of each disk on GET): 400 for a boot or virtual device (`HIDDEN_DISK_PREFIXES`), a partition and a name that is no disk of the host; 409 for the system disk, an NVMe disk (it manages its own power, and hdparm sets ATA disks), a disk without a serial that a rule can match (udev keeps `[A-Za-z0-9#+-.:=@_]`) or with the serial of another listed disk, a disk that udev knows by another serial than lsblk (`udevadm info`), and a host without hdparm.
- **hdparm is an optional host tool** (`OPTIONAL_HOST_TOOLS`, as exportfs, ADR-0321): `deploy/install.sh` installs it, but a host set up by hand may lack it; then every disk's `spindown_problem` is `NO_HDPARM`.
- **Power state without waking, with CHECK POWER MODE alone.** Each disk of GET /storage/disks gets `power_state` (active, standby, unknown) from `hdparm -C <disk>` on the host under its `timeout` (`disks.power_state`: TERM after 15 seconds, KILL 5 later, ADR-0258), read first; a disk in standby is not probed with wipefs (it counts as holding data). hdparm sends the disk CHECK POWER MODE alone and prints its answer as `drive state is:`: `active/idle`, `idle` and `NVcache_spinup` are active, `standby`, `sleeping` and `NVcache_spindown` standby; no such line, a failure (an exit status other than 0, as for a disk hdparm cannot ask) and the timeout are unknown. hdparm names only the answers 00h, 40h, 41h, 80h and FFh: for any other it prints `unknown` and exits 0, as for the Extended Power Conditions (EPC, ACS-2 on) that NAS drives with EPC timers enter, idle_a, idle_b, idle_c (81h-83h) and standby_y (01h). Then `smartctl -n idle -i -j <disk>` in the container asks again (`_epc_power_state`, at most 15 seconds, `run_in_container`, ADR-0290): smartctl sends CHECK POWER MODE first and, with `-n idle`, stops there for SLEEP, STANDBY, STANDBY_Y, IDLE and IDLE_A, IDLE_B, IDLE_C (the names of smartmontools' `ataprint.cpp`; the message is the one the SMART reads already find, as on the dev device), without IDENTIFY, with exit status bit 1 and the message "Device is in <MODE> mode", which `-j` puts in the JSON's `smartctl.messages` (`smartctl_stopped_in` finds it in both forms of the output). IDLE* is active, STANDBY* and SLEEP standby. When smartctl goes on to read the identity, the disk answered a mode it does not stop for (ACTIVE or IDLE, FFh, or an NV cache mode: the disk became active between the two reads) or one it does not name either, and that IDENTIFY says nothing of the mode: unknown, as when smartctl cannot open the disk or does not answer. The SMART reads below take STANDBY_Y as standby too. A SCSI disk's power condition, which smartctl reads from its sense data, takes several words in smartmontools' `scsiprint.cpp` (`STANDBY BY TIMER`, `STANDBY_Y BY COMMAND`, `IDLE_C BY TIMER`, `LOW POWER`, and `IDLE_ BY COMMAND` for IDLE_B): how it was reached is left out, LOW POWER (where smartctl stops as for SLEEP) and STANDBY* are standby, IDLE* active. Why hdparm, measured on the dev device's `sda` (WDC WD6400AACS-00G8B0, firmware 05.04C05, behind its JMB58x AHCI controller) with smartd off and no read or write counted in `/proc/diskstats`: with `hdparm -S 60` (5 minutes) or `-S 120` (10 minutes) and `hdparm -C` every 60 seconds, the disk went to standby after 660 s, so CHECK POWER MODE did not restart this disk's standby timer (no other disk was measured); put in standby with `hdparm -y`, it answered standby to `hdparm -C`, and `smartctl -n standby` left it asleep (exit status 2); with `-S 120`, `smartctl -n standby -i` (the earlier power read) every 3 minutes and `hdparm -C` every minute, it was still active after 840 s: smartctl also asks an awake disk IDENTIFY DEVICE, which restarts the timer, so every read of its power state kept it awake for another full timeout, and `scripts/dev/scenario.sh smart`, which read GET /storage/disks every 330 s, found it active after 990 s with no read or write counted. Where the host has no hdparm (an optional host tool: the host's `timeout` exits 127), and for an NVMe disk, which takes no ATA command and gets no idle timeout, `smartctl -n standby -i -j` in the container reads it, at most 15 seconds: it leaves a sleeping disk alone but restarts the timer of an awake one at every read. The Storage page asks for the disks alone and for the pools and the filesystems found on the disks only once they answered: those lists read every disk (below), and a read queued before the power mode's question would make a sleeping disk answer active. A line of the rule that UNOS did not write, or whose timeout is not offered (edited by hand), is no timeout and is dropped at the next change; a rule file that cannot be read is every disk's `spindown_problem`.
- **A disk that does not answer its power read keeps at most one hdparm on the host.** The host's `timeout` cannot end an hdparm stuck in the kernel (D state, in SG_IO) on a disk that stopped answering, and `run_on_host`'s limit (25 seconds) ends only nsenter; GET /storage/disks reads the disks one after another and the trash expiry reads them again. So `disks.power_state` bounds its hdparm per disk as `run_in_container` bounds its commands, for the same reasons (ADR-0290): one read of a disk at a time, a second waiting for the first at most that limit (thread-safe: GET /storage/disks and the trash expiry read in worker threads); after a read that timed out (`run_on_host`'s TimeoutExpired, or the host's `timeout` ended hdparm: 124 for TERM, or killed with KILL, which `timeout` sends to its own process group and so dies by too, -9 as nsenter passes it on, 137 through a shell), the disk is unknown at once, with no hdparm started for it, until `pgrep -f '^hdparm -C <disk>$'` (in the container, which has procps and the host's process IDs, `pid: host`; at most 5 seconds through `run_in_container`) finds none: then the next read runs. A pgrep that finds one, fails or does not answer starts nothing. The first read not started for a stuck one is logged, once.
- **SMART reads leave a sleeping disk asleep.** GET /storage/disks/{name}/smart, GET /health/disks, /health/disk/{device} and /health/overview run `smartctl -n standby -j -a`: a sleeping disk (SLEEP, STANDBY, or an EPC disk's STANDBY_Y) answers `power_state` standby with `healthy` null, or the health status `STANDBY` with lsblk's model, serial and size, and the overview counts it as `standby`. Starting a self-test still wakes it, as asked.
- **Every periodic disk access, audited** (`supervisor/tests/test_disk_spindown.py` runs each with every disk asleep on a fake host that wakes a disk for each command that reads it). ATA's standby timer runs while an awake disk receives no command that counts as use: IDENTIFY, which smartctl's SMART reads send too, restarts it (measured above for smartctl -i), CHECK POWER MODE did not on the dev device's disk, and anything asked of it hourly that restarts it would keep a disk with a timeout of an hour or more awake for good. Of the periodic reads, only the SMART monitor's still sends an awake disk IDENTIFY and SMART commands (`smartctl -n standby -j -a`): a disk without an idle timeout of UNOS's, one used since its last read, every awake disk at the first pass after each start of the supervisor (it runs at once, and `_disk_io_at_read` and `_disk_verdicts` start empty), and a disk that the last pass found asleep, which has no `_disk_io_at_read` entry, at the first pass that finds it awake, also when what woke it was no read or write (the IDLE of a Save's `hdparm -S`, a SMART test). The power reads send CHECK POWER MODE alone, except on a host without hdparm and for an NVMe disk (smartctl -i).
  - The SMART monitor (hourly, `-n standby`) leaves a sleeping disk alone, and does not read a disk with an idle timeout of UNOS's rule that the kernel counted no read or write on since its last read (`_disk_io_at_read`, `/proc/diskstats` through `disks.io_counts`): it keeps that read's verdict, as for a sleeping disk.
  - The RAID monitor (every 5 minutes) reads the pools without a scan of the disks (`pools_and_managed_names(scan=False)`: `btrfs filesystem show --mounted`, ioctls of the mounted pools, and lsblk's record of the others). btrfs-progs exits 1 without a word for `--mounted` when no btrfs filesystem is mounted: that is no pool mounted, not a failure, so a pool that is not mounted is still reported (ADR-0332).
  - `GET /api/v1/health/prometheus` and `/health/full`, which monitoring scrapes, count the pools the same way (`list_pools(scan=False)`).
  - The trash expiry (ADR-0259) checks every hour (`TRASH_EXPIRY_CHECK`) for the pools whose daily pass is due, asks only their disks whether they sleep (`spindown.pool_sleeps`: findmnt, lsblk and `disks.power_state`), and passes over a pool whose disks sleep, or cannot be asked; a check with no pass due asks no disk anything. A pass put off for a sleeping disk remembers that disk and the reads and writes the kernel had counted on it (`spindown.Asleep`, `disks.io_counts`): while they stay the same, the pool still sleeps and no disk of it is asked, and once they changed that disk is asked first. Otherwise each check would ask the pool's awake disks ahead of the sleeping one in lsblk's order, and where that restarts their timers (smartctl's power read, on a host without hdparm) a raid1 pool whose reads all go to one disk (btrfs picks the mirror by the reader's pid, and `noatime` reads write nothing) would keep that disk awake while the other sleeps.
  - smartd, the host's SMART daemon, which the package smartmontools starts when it is installed (`deploy/install.sh` installs it, ADR-0002): with Debian's `/etc/smartd.conf` (`DEVICESCAN` with `-n standby`) it leaves a sleeping disk alone, but asks every awake disk its power mode and reads its SMART status, attributes and logs every 30 minutes (on the dev device, while it ran, `sda` given 20 minutes was still awake after 22). UNOS reads SMART itself (Disk Health and the SMART monitor's alerts, ADR-0235, ADR-0332), so `install.sh` turns smartd off once UNOS runs (`stop_smartd`: `systemctl disable --now smartmontools`), and so does the manual installation of `docs/INSTALL.md`; `uninstall.sh` leaves it off and says how to turn it on again.
  - The live statistics read `/proc/diskstats` only. The task check, the UPS monitor and the events socket's problems touch no data disk; scrub statuses are read only while a scrub runs.
- **Uninstallation.** `deploy/uninstall.sh` (`remove_disk_idle_timeouts`, right after the containers, the supervisor's among them, and the `unos` service have stopped, so that the supervisor cannot write the rule again, and before `remove_files` removes `/opt/unos` and the script with it, since `install.sh` puts it nowhere else) first undoes on each disk that UNOS's rule names what UNOS set, with the host's tools, since the supervisor's container, whose smartctl UNOS used, is gone (the script adds `/usr/sbin`, `/usr/bin`, `/sbin` and `/bin` after the PATH it was given: `su` without `-` keeps a user's PATH, which on Debian has no `/usr/sbin` and `/sbin`): `hdparm -S 0` for a disk's line, as Off does, and `smartctl -o on -c` for a disk whose record says UNOS turned its automatic offline data collection off (a setting the drive is expected to keep across power cycles: assumed, not confirmed, above); each under the host's `timeout` (TERM after 30 seconds, KILL 5 later, which `timeout` sends to its own process group and so dies of too: the script goes on after at most 35 seconds per command, but a command that the kernel holds in uninterruptible sleep, as for a disk that does not answer, outlives the KILL until the kernel lets it go; smartctl's answer therefore goes to a temporary file of `mktemp`, read once `timeout` has returned and then removed, not through a pipe whose end a stuck smartctl would keep open, and bash's own "Killed" line is not shown), the timeout first, whose IDLE wakes the disk for the second. Without `hdparm -S 0` the disk would keep UNOS's timeout until its next power cycle. smartctl exits 0 without sending `-o` to a disk with SMART off (`ataprint.cpp`), so `-c` reads the collection back, as the supervisor does, and only its line "Auto Offline Data Collection: Enabled." counts as on. Then the rule goes, as `/etc/unos` and UNOS's NFS export file go, and `udevadm control --reload` runs where the host has udevadm (a failure is only reported: udev reads a changed rules folder by itself); a run stopped before (a dropped SSH session, Ctrl-C) finds the rule whole again, with the script still there to run. `timeout` runs hdparm and smartctl in a process group of their own, which Ctrl-C does not reach, and bash goes on after a SIGINT that its command survived: so while the disks are undone the script notes a Ctrl-C or a TERM, and once the command then running has ended (35 seconds at most) it ends the uninstallation with the rule whole (status 130 or 143) and says to run it again. A disk whose collection is still off (not attached, not alone with its serial, no smartctl on the host, a failure) keeps its record: the rule is replaced by a header and those records alone (written next to it and renamed, as the supervisor writes it; a file `<rule>.unos-tmp.<pid>` that a run killed in between left, which udev does not read, the next run removes, and no file of another name), comments that udev runs nothing of and that `read_rule` takes as records without a timeout, so that a new installation's Off turns the collection on, and another run of the script tries again (from a checkout of UNOS once a run has ended, since it removes `/opt/unos`). When that write fails, the rule is removed all the same, since its lines would set the timeouts at every boot, and the end names those disks. The file is read as text and never run, and only the lines that `read_rule` takes as UNOS's count: read as udev reads a rules file without NUL bytes, as UNOS writes it (a line ends at `\n` or `\r`, and only spaces and tabs around it are blanks; `read_rule` reads it so too; udev also ends a line at a NUL byte), the exact form that `render` writes, a serial that `_RULE_SERIAL` accepts and the `hdparm -S` value of an offered timeout in ASCII digits, all spelled out in the script so that no locale changes them (a test holds the script to `read_rule`'s choice, in the C and a UTF-8 locale). A rule that holds a NUL byte is not read: bash drops NUL bytes from what it reads, which would join the parts of a line around one into a line of UNOS's that neither `read_rule` nor udev (which ends a line at a NUL) takes. A disk is found by its serial among the whole disks of `lsblk -dnr -o NAME,TYPE,SERIAL` (udev's records and sysfs: no disk is read); a serial that no disk or more than one disk reports is not touched, nor is any disk that no counted line names. A rule that cannot be read, or that holds a NUL byte, stays: it is the only record of the disks whose scans are off. Nothing of this stops the uninstallation (`set -e`); its last text names what is left: a rule not read, with what to run and `rm`; a rule that could not be removed, which sets the timeouts again at every boot, with `rm`; each timeout or scans setting not undone, with why (the host has no hdparm or smartctl, the disk is not attached or not alone with its serial, lsblk or the command failed or did not answer, no temporary file for smartctl's answer could be made, smartctl did not show the collection on) and the exact command, `DISK` standing for a path that is not known, with how to find it (for a disk with SMART off, to which smartctl sends no `-o`, the command is `smartctl -s on -o on`, which turns SMART on too: the uninstallation does not run it, since UNOS did not turn SMART off); a rule left with records, with `rm` once the collection is on; and the lines other than comments that are not UNOS's, as printable ASCII (a control character could drive the terminal), for which nothing ran and which are no longer in the rule. It also says that the disks whose timeout it turned off have no standby timer until they restart, or until the boot that applies a rule it could not remove. `confirm_uninstall` lists the step.
- **Device check.** `scripts/dev/scenario.sh smart` accepts STANDBY in the SMART reads of a disk that already sleeps, shows the system disk refused a timeout with its reason (on the dev device the boot SD card, a boot device: 400), sets the first data hard disk's shortest timeout, waits for standby (the timeout and 30 s, at most six times: 1980 s, stopping at the first standby; it covers a disk that sleeps later than the timeout, as the dev device's after about 10 minutes for 5 (660 s), since its reads of GET /storage/disks no longer restart the timer, and one more such minimum after a pass of the SMART monitor that reads the awake disk during the wait, which is right when the disk was used since its last read, as in `scenario.sh all`, where the files and volumes checks write to the pool just before smart: with three times, 990 s, a pass between about 360 s and 990 s into the wait left the disk awake at the end; a disk still awake after 1980 s fails the step, which says whether the kernel counted reads or writes on it meanwhile), reads SMART through both pages and shows the disk asleep with its I/O counters unchanged, and sets the timeout of UNOS's rule again. Around those steps it reads the disk's automatic offline data collection with `smartctl -i -c -j` in the supervisor's container (`docker exec`, as the restore check does, ADR-0183; `-n never` first, which wakes a sleeping disk as the Save after it does, then `-n standby` on the disk the Save woke): first as found, failing when UNOS's rule records it off but it is on; right after the Save, off, and recorded when UNOS turned it off (or left as found for a disk without it); in the wait step, a disk still awake with no read or write counted and the collection on is failed with that cause; and with the timeout restored, as found, where an answer with a `warning` fails too. Its clean-up, after it set the timeout as found, reads the collection and UNOS's record of it once more (`-n never`) and fails unless they are as found, naming what it left and the way back (save Off or the timeout again, or `smartctl -o on|off`): the final comparison reads neither, since its first read would wake a sleeping disk. A disk with a timeout of UNOS's whose collection is on unrecorded (set before this, or UNOS could not turn it off), and a record without a timeout (an Off that could not turn it on), are SKIPs with the reason: the check's Save or Off would change the collection for good. With none there, its Off leaves no standby timer (`hdparm -S 0`) until the disk's next power cycle, since ATA reads no timer back; so when `/etc/hdparm.conf` sets one (Debian's `85-hdparm.rules` applies it at boot), the timeout steps are SKIPs with that reason, as they are without hdparm on the host.
- **Tests.** `supervisor/tests/test_disk_spindown.py`, the scenario's in `supervisor/tests/test_dev_scenarios.py`, smartd's and the uninstallation's in `supervisor/tests/test_deploy_scripts.py` (with stubs of the host's tools, never the host's own), `webui/tests/storage.spec.ts`, `webui/tests/health.spec.ts`, `webui/tests/mobile-layout.spec.ts` (the dialog).

## Consequences

- A disk may sleep later than the timeout set when it has a minimum of its own, which ATA does not report: `hdparm -I` of the dev device's WD6400AACS says "Standby timer values: spec'd by Standard, with device specific minimum", and given 5 minutes it slept after about 10 (660 s, as given 10). The Storage page shows the timeout set.
- That hdparm -C leaves an awake disk's standby timer running was measured on the dev device's disk alone; a disk that counts CHECK POWER MODE as use would stay awake for another full timeout at each load of the Storage page and each power read of a due trash pass, as with smartctl -i, and the device check's wait step would fail with no read or write counted.
- An EPC disk in idle_a, idle_b, idle_c or standby_y is read with two commands, hdparm on the host and smartctl in the container, both CHECK POWER MODE alone. It is still unknown when smartctl cannot open it although hdparm could, and when it became active between the two reads (smartctl's IDENTIFY then restarts its timer, as the use that made it active did).
- A disk that stops answering its power read keeps one stuck hdparm on the host, as ADR-0290 keeps one process of each command in the container, until the kernel lets it go or the host reboots; meanwhile its power is unknown at once, the power read holds up the Storage page and the trash expiry only for the first read's 25 seconds (a second read that overlaps the first waits at most as long), and each read of it runs one pgrep in the container. A read that the host's `timeout` ended (124, or killed) also costs one pgrep before the next read. Unknown counts as awake, as before: GET /storage/disks still probes such a disk with wipefs, which is not bounded this way (30 seconds of `run_on_host` at each load, and a wipefs that may stay stuck on the host), and the trash expiry does not pass over its pool for it.
- On a host without hdparm, and for an NVMe disk, each read of an awake disk's power state (a load of the Storage page, a trash pass that is due) restarts its standby timer: a timer of the disk's own, since UNOS sets none there.
- Saving a timeout spins the disk up (IDLE). Off runs `hdparm -S 0` and removes the line: the disk has no standby timer until its next power cycle, not even one of `/etc/hdparm.conf` or of its own default, and after one it keeps what those set, which UNOS does not read.
- The RAID monitor and the monitoring endpoints no longer count the missing devices or the bytes used of a pool that is not mounted, and a label changed while it was mounted can be stale in udev's record until the disk appears again. Pages that list the pools or the filesystems to import still scan the disks when an administrator opens them (`btrfs filesystem show` without `--mounted` probes every block device through libblkid) and can spin up a sleeping disk: one that no mounted pool holds open, and a mounted pool's disk too unless the kernel's cache answers the probe, which the device check observes. They are the dashboard (an administrator's first page after signing in), Storage, Shares (`GET /shares/paths`), Snapshots (`GET /snapshots/subvolumes`) and System > Scheduler.
- The Storage page asks each disk's power mode at each load, and shows the pools a moment later than before, after the disks. A pool whose disks always sleep at the hourly checks keeps its trash longer, and so does one whose remembered sleeping disk was woken by a command that is no read or write (a SMART test, a timeout set), until its next read or write.
- smartd no longer runs on a host that `install.sh` or `docs/INSTALL.md` set up: what an owner had set in `/etc/smartd.conf` (mail, scheduled self-tests) stops too, which UNOS's alerts and the Scheduler's SMART tests replace. A host set up before, such as the dev device (set up by hand, ADR-0376), keeps smartd as it is (ADR-0207): while it runs with Debian's configuration, a timeout of 30 minutes or more takes effect only on a disk that does not count smartd's commands as use. Turning it off is a host-level change (ADR-0018): smartd is off on the dev device now, as `stop_smartd` leaves it, but `install.sh` has not run there at all.
- A disk with an idle timeout that stays unused is not read by the SMART monitor: a self-test that fails while it is idle is reported once the disk is used again, as for a sleeping disk. A disk without one is read every hour, as before.
- A disk with a timeout of UNOS's runs no automatic offline scans of its own: fewer surface scans, so a sector that went bad where nothing reads may be found later (the drive counts it in its pending sectors only when something reads it). A scheduled scrub (System > Scheduler) reads every used block of its pool instead; a long SMART test reads the whole surface, but UNOS does not schedule one yet: the Scheduler's SMART Test tasks run `smartctl -t short`, and no page starts a test (`POST /api/v1/health/disk/{name}/test?test_type=long` exists, without a caller in the web UI). Until a long test can be scheduled, the surface outside the pools' data is read only when the administrator runs one. The Storage page's dialog and `docs/USER_GUIDE.md` say so.
- If a drive does not keep the setting across a power cycle, its timeout stops working again after each one until the next Save; nothing reads it back but the device check. The setting stays with the drive when it moves to another machine, until UNOS's Off turns it on or someone runs `smartctl -o on`.
- The rule file holds a record line per disk whose scans UNOS turned off: a disk removed for good keeps its record, as it keeps its line.
- After an uninstallation, a disk that had a timeout of UNOS has no standby timer until its next power cycle (`hdparm -S 0` wakes it if it sleeps, as Off does), then its own or the one of `/etc/hdparm.conf`. A disk whose collection could not be turned on again (one not attached, say) keeps it off until someone runs `smartctl -o on` on it (`-s on -o on` where SMART is off), or a new installation's Off or another run of the uninstallation (from a checkout of UNOS) does: until then UNOS's rule stays, as comments and that disk's record, which udev ignores, and the end of the uninstallation says to remove it once the collection is on. A line edited by hand goes with the rule, as it does at the supervisor's next write of the rule: the uninstallation shows it, as printable ASCII, and runs nothing for it. A line with other blanks around it than spaces and tabs, or a value in other digits than ASCII's, is no line of UNOS's for `read_rule` either.
- Scheduled tasks (scrubs, SMART tests, snapshots, backups, custom commands) wake the disks they need: the administrator scheduled them.
- Two disks that report one serial (identical USB bridges) get no timeout.

## Considered options

- A table of timeouts with a startup reconcile and a hotplug watcher in the supervisor: a second copy of what the host does, and a spin-up at every start.
- `smartctl -n standby -i` for every disk's power state (the first version): always there, in the container, and no need of the host's hdparm, but its IDENTIFY restarts an awake disk's standby timer (measured above), so each load of the Storage page and each power read of the trash expiry kept the disk awake for another full timeout.
- Offering only timeouts below the hourly checks (to 30 minutes), or leaving every unused disk unread by the SMART monitor: the first drops the timeouts of hours that a NAS in daily use wants, the second would also stop the hourly reads of disks that have no timeout.
- Leaving smartd on and stating the limit: six of the nine offered timeouts, 30 minutes and more, would not take effect on a new installation for a disk that counts its commands as use. A `/etc/smartd.conf` that leaves out the disks of UNOS's rule: the host's own file (as `/etc/hdparm.conf`), rewritten at every change of a timeout, with a restart of smartd, and smartd would still watch what UNOS's SMART monitor already watches.
- For the disk's own automatic offline scans: leaving them on and only warning, which keeps a timeout of UNOS's from working on such a disk for most of the time, the case measured; turning them off for every data disk, also one without a timeout, which takes surface scans from disks that gain nothing from it; and a udev rule that runs `smartctl -o off` whenever the disk appears, which needs smartctl on the host (UNOS runs it in its container, and a host set up by hand may lack it), would send a SMART command at every boot, and is not needed while the drive keeps the setting itself (the risk stated above).
- For the uninstallation: keeping the rule and naming it, as the K1's NVMe rule is kept (ADR-0370), which would set UNOS's timeouts at every boot of a host without UNOS and leave the scans off for good; removing it without `hdparm -S 0`, which would leave UNOS's timeouts until the next power cycle; removing it before the disks are done, which leaves a run stopped on the way without the records it needs; keeping the whole rule while some disk's scans could not be turned on, which would also keep its timeouts at every boot (the records alone set none); a byte-for-byte copy of the rule in `/var/lib/unos/backups`, which neither a new installation nor another run reads; taking `smartctl -o on`'s exit status alone, which is 0 for a disk with SMART off; running the step after `remove_files` (its first place), which left a run stopped in it without the script to run again; reading smartctl's answer through a command substitution, whose pipe a smartctl stuck in the kernel keeps open past the KILL, so that the script waits as long as the kernel holds it; leaving Ctrl-C to bash, which goes on after a SIGINT that the command under `timeout` survived; and keeping the lines edited by hand, in UNOS's rule or a file of their own, which the supervisor's own writes of the rule drop and which may set again what Off undid.
