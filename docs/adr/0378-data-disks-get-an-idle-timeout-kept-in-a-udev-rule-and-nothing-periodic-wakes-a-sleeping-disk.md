# ADR-0378: Data disks get an idle timeout that UNOS keeps in a udev rule, and nothing UNOS does periodically wakes a sleeping disk

## Context

`storage.disk-spindown` asks for an idle timeout per data disk, refused for the system disk, and a Storage page that shows whether each disk sleeps while reading SMART data does not wake it. Disk Health woke every disk (`smartctl` without `-n standby`, ADR-0235), and so did the RAID monitor every 5 minutes for a disk that no mounted pool holds open: `btrfs filesystem show` reads the superblock of every block device through libblkid. The owner's words for this batch (in translation): "then we continue developing UNOS's features with our test hardware in mind", under the standing delegation "work on through the features, ask no questions; I allow everything" (as ADR-0340). The dev device's only data disk is the pool's 640 GB SATA hard disk `sda` behind a JMicron AHCI controller (ADR-0376), and its host has hdparm (installed by the owner for this entry).

## Decision

- **Values.** Off or 5, 10, 20, 30 minutes, 1, 2, 3, 4 or 5 hours (`SPINDOWN_MINUTES` of `supervisor/src/storage/schemas.py`): what `hdparm -S` expresses (5-second steps to 20 minutes, `-S 1` to `240`; 30-minute steps from 30 minutes to 5.5 hours, `241` to `251`), from 5 minutes, below which a disk of a quiet NAS spins down between the bursts of one session and wears with each start, to whole hours. `hdparm_value` and `minutes_of` of `supervisor/src/storage/spindown.py` convert.
- **Setting.** `PUT /api/v1/storage/disks/{name}/spindown` with `{"minutes": n}` (administrators, ADR-0030; 422 for a value not offered) runs `hdparm -S <value> /dev/<disk>` on the host under `timeout` (ADR-0020, ADR-0258) and then writes UNOS's udev rule `/etc/udev/rules.d/90-unos-disk-spindown.rules` (`write_host_file_atomic`), one line per disk: `ACTION=="add", SUBSYSTEM=="block", ENV{DEVTYPE}=="disk", ENV{ID_SERIAL_SHORT}=="<serial>", RUN+="/sbin/hdparm -S <value> $devnode"`, then `udevadm control --reload` (a failure is logged: udevd sees a changed rules folder by itself). The file is written only when a disk's line changes, removed when no line is left (ADR-0214), and keeps only UNOS's lines. A change is audited as `settings_changed` of the resource `disk` (ADR-0351); hdparm's failure answers 500 and keeps nothing; a rule that cannot be written after hdparm set the timeout answers 500, saying the disk has it until it restarts, and is audited as failed (ADR-0350).
- **Kept in the udev rule, not in a table or the supervisor.** udev runs the line whenever the disk appears, at boot before the supervisor starts and when it is plugged in again under any name, matched by the serial; the supervisor would need a watcher for new disks and would send `hdparm -S`, whose IDLE command spins a sleeping disk up, at each of its own starts. The rule is the setting's only home, as a pool's fstab entry is its mount's (ADR-0283): GET /storage/disks reads it back (`spindown`), and no table can disagree with what the host does. Debian's `/etc/hdparm.conf` is left to the owner: it is the host's own file.
- **Refused with the reason** (`spindown.problem`, also as `spindown_problem` of each disk on GET): 400 for a boot or virtual device (`HIDDEN_DISK_PREFIXES`), a partition and a name that is no disk of the host; 409 for the system disk, an NVMe disk (it manages its own power, and hdparm sets ATA disks), a disk without a serial that a rule can match (udev keeps `[A-Za-z0-9#+-.:=@_]`) or with the serial of another listed disk, a disk that udev knows by another serial than lsblk (`udevadm info`), and a host without hdparm.
- **hdparm is an optional host tool** (`OPTIONAL_HOST_TOOLS`, as exportfs, ADR-0321): `deploy/install.sh` installs it, but a host set up by hand may lack it; then every disk's `spindown_problem` is `NO_HDPARM`.
- **Power state without waking, with CHECK POWER MODE alone.** Each disk of GET /storage/disks gets `power_state` (active, standby, unknown) from `hdparm -C <disk>` on the host under its `timeout` (`disks.power_state`: TERM after 15 seconds, KILL 5 later, ADR-0258), read first; a disk in standby is not probed with wipefs (it counts as holding data). hdparm sends the disk CHECK POWER MODE alone and prints its answer as `drive state is:`: `active/idle`, `idle` and `NVcache_spinup` are active, `standby`, `sleeping` and `NVcache_spindown` standby; no such line, a failure (an exit status other than 0, as for a disk hdparm cannot ask) and the timeout are unknown. hdparm names only the answers 00h, 40h, 41h, 80h and FFh: for any other it prints `unknown` and exits 0, as for the Extended Power Conditions (EPC, ACS-2 on) that NAS drives with EPC timers enter, idle_a, idle_b, idle_c (81h-83h) and standby_y (01h). Then `smartctl -n idle -i -j <disk>` in the container asks again (`_epc_power_state`, at most 15 seconds, `run_in_container`, ADR-0290): smartctl sends CHECK POWER MODE first and, with `-n idle`, stops there for SLEEP, STANDBY, STANDBY_Y, IDLE and IDLE_A, IDLE_B, IDLE_C (the names of smartmontools' `ataprint.cpp`; the message is the one the SMART reads already find, as on the dev device), without IDENTIFY, with exit status bit 1 and the message "Device is in <MODE> mode", which `-j` puts in the JSON's `smartctl.messages` (`smartctl_stopped_in` finds it in both forms of the output). IDLE* is active, STANDBY* and SLEEP standby. When smartctl goes on to read the identity, the disk answered a mode it does not stop for (ACTIVE or IDLE, FFh, or an NV cache mode: the disk became active between the two reads) or one it does not name either, and that IDENTIFY says nothing of the mode: unknown, as when smartctl cannot open the disk or does not answer. The SMART reads below take STANDBY_Y as standby too. Why hdparm, measured on the dev device's `sda` (WDC WD6400AACS-00G8B0, firmware 05.04C05, behind its JMB58x AHCI controller) with smartd off and no read or write counted in `/proc/diskstats`: with `hdparm -S 60` (5 minutes) or `-S 120` (10 minutes) and `hdparm -C` every 60 seconds, the disk went to standby after 660 s, so CHECK POWER MODE did not restart this disk's standby timer (no other disk was measured); put in standby with `hdparm -y`, it answered standby to `hdparm -C`, and `smartctl -n standby` left it asleep (exit status 2); with `-S 120`, `smartctl -n standby -i` (the earlier power read) every 3 minutes and `hdparm -C` every minute, it was still active after 840 s: smartctl also asks an awake disk IDENTIFY DEVICE, which restarts the timer, so every read of its power state kept it awake for another full timeout, and `scripts/dev/scenario.sh smart`, which read GET /storage/disks every 330 s, found it active after 990 s with no read or write counted. Where the host has no hdparm (an optional host tool: the host's `timeout` exits 127), and for an NVMe disk, which takes no ATA command and gets no idle timeout, `smartctl -n standby -i -j` in the container reads it, at most 15 seconds: it leaves a sleeping disk alone but restarts the timer of an awake one at every read. The Storage page asks for the disks alone and for the pools and the filesystems found on the disks only once they answered: those lists read every disk (below), and a read queued before the power mode's question would make a sleeping disk answer active. A line of the rule that UNOS did not write, or whose timeout is not offered (edited by hand), is no timeout and is dropped at the next change; a rule file that cannot be read is every disk's `spindown_problem`.
- **A disk that does not answer its power read keeps at most one hdparm on the host.** The host's `timeout` cannot end an hdparm stuck in the kernel (D state, in SG_IO) on a disk that stopped answering, and `run_on_host`'s limit (25 seconds) ends only nsenter; GET /storage/disks reads the disks one after another and the trash expiry reads them again. So `disks.power_state` bounds its hdparm per disk as `run_in_container` bounds its commands, for the same reasons (ADR-0290): one read of a disk at a time, a second waiting for the first at most that limit (thread-safe: GET /storage/disks and the trash expiry read in worker threads); after a read that timed out (`run_on_host`'s TimeoutExpired, or 124 or 137 from the host's `timeout`), the disk is unknown at once, with no hdparm started for it, until `pgrep -f '^hdparm -C <disk>$'` (in the container, which has procps and the host's process IDs, `pid: host`; at most 5 seconds through `run_in_container`) finds none: then the next read runs. A pgrep that finds one, fails or does not answer starts nothing. The first read not started for a stuck one is logged, once.
- **SMART reads leave a sleeping disk asleep.** GET /storage/disks/{name}/smart, GET /health/disks, /health/disk/{device} and /health/overview run `smartctl -n standby -j -a`: a sleeping disk (SLEEP, STANDBY, or an EPC disk's STANDBY_Y) answers `power_state` standby with `healthy` null, or the health status `STANDBY` with lsblk's model, serial and size, and the overview counts it as `standby`. Starting a self-test still wakes it, as asked.
- **Every periodic disk access, audited** (`supervisor/tests/test_disk_spindown.py` runs each with every disk asleep on a fake host that wakes a disk for each command that reads it). ATA's standby timer runs while an awake disk receives no command that counts as use: IDENTIFY, which smartctl's SMART reads send too, restarts it (measured above for smartctl -i), CHECK POWER MODE did not on the dev device's disk, and anything asked of it hourly that restarts it would keep a disk with a timeout of an hour or more awake for good. Of the periodic reads, only the SMART monitor's still sends an awake disk IDENTIFY and SMART commands (`smartctl -n standby -j -a`): a disk without an idle timeout of UNOS's, one used since its last read, every awake disk at the first pass after each start of the supervisor (it runs at once, and `_disk_io_at_read` and `_disk_verdicts` start empty), and a disk that the last pass found asleep, which has no `_disk_io_at_read` entry, at the first pass that finds it awake, also when what woke it was no read or write (the IDLE of a Save's `hdparm -S`, a SMART test). The power reads send CHECK POWER MODE alone, except on a host without hdparm and for an NVMe disk (smartctl -i).
  - The SMART monitor (hourly, `-n standby`) leaves a sleeping disk alone, and does not read a disk with an idle timeout of UNOS's rule that the kernel counted no read or write on since its last read (`_disk_io_at_read`, `/proc/diskstats` through `disks.io_counts`): it keeps that read's verdict, as for a sleeping disk.
  - The RAID monitor (every 5 minutes) reads the pools without a scan of the disks (`pools_and_managed_names(scan=False)`: `btrfs filesystem show --mounted`, ioctls of the mounted pools, and lsblk's record of the others). btrfs-progs exits 1 without a word for `--mounted` when no btrfs filesystem is mounted: that is no pool mounted, not a failure, so a pool that is not mounted is still reported (ADR-0332).
  - `GET /api/v1/health/prometheus` and `/health/full`, which monitoring scrapes, count the pools the same way (`list_pools(scan=False)`).
  - The trash expiry (ADR-0259) checks every hour (`TRASH_EXPIRY_CHECK`) for the pools whose daily pass is due, asks only their disks whether they sleep (`spindown.pool_sleeps`: findmnt, lsblk and `disks.power_state`), and passes over a pool whose disks sleep, or cannot be asked; a check with no pass due asks no disk anything. A pass put off for a sleeping disk remembers that disk and the reads and writes the kernel had counted on it (`spindown.Asleep`, `disks.io_counts`): while they stay the same, the pool still sleeps and no disk of it is asked, and once they changed that disk is asked first. Otherwise each check would ask the pool's awake disks ahead of the sleeping one in lsblk's order, and where that restarts their timers (smartctl's power read, on a host without hdparm) a raid1 pool whose reads all go to one disk (btrfs picks the mirror by the reader's pid, and `noatime` reads write nothing) would keep that disk awake while the other sleeps.
  - smartd, the host's SMART daemon, which the package smartmontools starts when it is installed (`deploy/install.sh` installs it, ADR-0002): with Debian's `/etc/smartd.conf` (`DEVICESCAN` with `-n standby`) it leaves a sleeping disk alone, but asks every awake disk its power mode and reads its SMART status, attributes and logs every 30 minutes (on the dev device, while it ran, `sda` given 20 minutes was still awake after 22). UNOS reads SMART itself (Disk Health and the SMART monitor's alerts, ADR-0235, ADR-0332), so `install.sh` turns smartd off once UNOS runs (`stop_smartd`: `systemctl disable --now smartmontools`), and so does the manual installation of `docs/INSTALL.md`; `uninstall.sh` leaves it off and says how to turn it on again.
  - The live statistics read `/proc/diskstats` only. The task check, the UPS monitor and the events socket's problems touch no data disk; scrub statuses are read only while a scrub runs.
- **Device check.** `scripts/dev/scenario.sh smart` accepts STANDBY in the SMART reads of a disk that already sleeps, shows the system disk refused a timeout with its reason (on the dev device the boot SD card, a boot device: 400), sets the first data hard disk's shortest timeout, waits for standby (the timeout and 30 s, at most six times: 1980 s, stopping at the first standby; it covers a disk that sleeps later than the timeout, as the dev device's after about 10 minutes for 5 (660 s), since its reads of GET /storage/disks no longer restart the timer, and one more such minimum after a pass of the SMART monitor that reads the awake disk during the wait, which is right when the disk was used since its last read, as in `scenario.sh all`, where the files and volumes checks write to the pool just before smart: with three times, 990 s, a pass between about 360 s and 990 s into the wait left the disk awake at the end; a disk still awake after 1980 s fails the step, which says whether the kernel counted reads or writes on it meanwhile), reads SMART through both pages and shows the disk asleep with its I/O counters unchanged, and sets the timeout of UNOS's rule again. With none there, its Off leaves no standby timer (`hdparm -S 0`) until the disk's next power cycle, since ATA reads no timer back; so when `/etc/hdparm.conf` sets one (Debian's `85-hdparm.rules` applies it at boot), the timeout steps are SKIPs with that reason, as they are without hdparm on the host.
- **Tests.** `supervisor/tests/test_disk_spindown.py`, the scenario's in `supervisor/tests/test_dev_scenarios.py`, smartd's in `supervisor/tests/test_deploy_scripts.py`, `webui/tests/storage.spec.ts`, `webui/tests/health.spec.ts`, `webui/tests/mobile-layout.spec.ts` (the dialog).

## Consequences

- A disk may sleep later than the timeout set when it has a minimum of its own, which ATA does not report: `hdparm -I` of the dev device's WD6400AACS says "Standby timer values: spec'd by Standard, with device specific minimum", and given 5 minutes it slept after about 10 (660 s, as given 10). The Storage page shows the timeout set.
- That hdparm -C leaves an awake disk's standby timer running was measured on the dev device's disk alone; a disk that counts CHECK POWER MODE as use would stay awake for another full timeout at each load of the Storage page and each power read of a due trash pass, as with smartctl -i, and the device check's wait step would fail with no read or write counted.
- An EPC disk in idle_a, idle_b, idle_c or standby_y is read with two commands, hdparm on the host and smartctl in the container, both CHECK POWER MODE alone. It is still unknown when smartctl cannot open it although hdparm could, and when it became active between the two reads (smartctl's IDENTIFY then restarts its timer, as the use that made it active did).
- A disk that stops answering its power read keeps one stuck hdparm and its `timeout` on the host, as ADR-0290 keeps one process of each command in the container, until the kernel lets it go or the host reboots; meanwhile its power is unknown at once, the power read holds up the Storage page and the trash expiry only for the first read's 25 seconds (a second read that overlaps the first waits at most as long), and each read of it runs one pgrep in the container. A read that the host's `timeout` ended (124, 137) also costs one pgrep before the next read. Unknown counts as awake, as before: GET /storage/disks still probes such a disk with wipefs, which is not bounded this way (30 seconds of `run_on_host` at each load, and a wipefs that may stay stuck on the host), and the trash expiry does not pass over its pool for it.
- On a host without hdparm, and for an NVMe disk, each read of an awake disk's power state (a load of the Storage page, a trash pass that is due) restarts its standby timer: a timer of the disk's own, since UNOS sets none there.
- Saving a timeout spins the disk up (IDLE). Off runs `hdparm -S 0` and removes the line: the disk has no standby timer until its next power cycle, not even one of `/etc/hdparm.conf` or of its own default, and after one it keeps what those set, which UNOS does not read.
- The RAID monitor and the monitoring endpoints no longer count the missing devices or the bytes used of a pool that is not mounted, and a label changed while it was mounted can be stale in udev's record until the disk appears again. Pages that list the pools or the filesystems to import still scan the disks when an administrator opens them (`btrfs filesystem show` without `--mounted` probes every block device through libblkid) and can spin up a sleeping disk: one that no mounted pool holds open, and a mounted pool's disk too unless the kernel's cache answers the probe, which the device check observes. They are the dashboard (an administrator's first page after signing in), Storage, Shares (`GET /shares/paths`), Snapshots (`GET /snapshots/subvolumes`) and System > Scheduler.
- The Storage page asks each disk's power mode at each load, and shows the pools a moment later than before, after the disks. A pool whose disks always sleep at the hourly checks keeps its trash longer, and so does one whose remembered sleeping disk was woken by a command that is no read or write (a SMART test, a timeout set), until its next read or write.
- smartd no longer runs on a host that `install.sh` or `docs/INSTALL.md` set up: what an owner had set in `/etc/smartd.conf` (mail, scheduled self-tests) stops too, which UNOS's alerts and the Scheduler's SMART tests replace. A host set up before, such as the dev device (set up by hand, ADR-0376), keeps smartd as it is (ADR-0207): while it runs with Debian's configuration, a timeout of 30 minutes or more takes effect only on a disk that does not count smartd's commands as use. Turning it off is a host-level change (ADR-0018): smartd is off on the dev device now, as `stop_smartd` leaves it, but `install.sh` has not run there at all.
- A disk with an idle timeout that stays unused is not read by the SMART monitor: a self-test that fails while it is idle is reported once the disk is used again, as for a sleeping disk. A disk without one is read every hour, as before.
- Scheduled tasks (scrubs, SMART tests, snapshots, backups, custom commands) wake the disks they need: the administrator scheduled them.
- Two disks that report one serial (identical USB bridges) get no timeout.

## Considered options

- A table of timeouts with a startup reconcile and a hotplug watcher in the supervisor: a second copy of what the host does, and a spin-up at every start.
- `smartctl -n standby -i` for every disk's power state (the first version): always there, in the container, and no need of the host's hdparm, but its IDENTIFY restarts an awake disk's standby timer (measured above), so each load of the Storage page and each power read of the trash expiry kept the disk awake for another full timeout.
- Offering only timeouts below the hourly checks (to 30 minutes), or leaving every unused disk unread by the SMART monitor: the first drops the timeouts of hours that a NAS in daily use wants, the second would also stop the hourly reads of disks that have no timeout.
- Leaving smartd on and stating the limit: six of the nine offered timeouts, 30 minutes and more, would not take effect on a new installation for a disk that counts its commands as use. A `/etc/smartd.conf` that leaves out the disks of UNOS's rule: the host's own file (as `/etc/hdparm.conf`), rewritten at every change of a timeout, with a restart of smartd, and smartd would still watch what UNOS's SMART monitor already watches.
