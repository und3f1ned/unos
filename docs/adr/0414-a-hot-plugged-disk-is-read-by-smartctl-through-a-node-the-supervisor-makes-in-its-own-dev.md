# ADR-0414: A disk attached after the supervisor started is read by smartctl through a node that the supervisor makes in its own /dev from the host's sysfs

## Context

smartctl runs in the supervisor's container (ADR-0290), whose `/dev` Docker fills with the host's device nodes once, when the container starts: a disk attached later, such as a USB disk, has no node there, so its SMART data, its self-tests, the SMART monitor's records of it and the power read of smartctl failed with "No such device" until the supervisor restarted, while lsblk on the host listed it (ADR-0360, `storage.hot-plugged-disks-smart`). The entry named three ways out: the host's `/dev` in the container, another way to add the new nodes, or smartctl on the host. The agent chose under the owner's standing delegation (as in ADR-0378), which for this batch asks above all that the choice be safe, keeping what ADR-0290 and ADR-0378 give: a smartctl stuck in the kernel holds no worker thread, one run of a command at a time, and power reads that never wake a sleeping disk.

## Decision

- **Every smartctl goes through `host.run_smartctl(options, device, timeout=...)`** (`supervisor/src/host.py`), which calls `container_disk_node(device)` and then `run_in_container(["smartctl", *options, device])` unchanged (ADR-0290): Disk Health's reads, the overview and the self-test (`supervisor/src/health/router.py`), the SMART monitor's snapshots, the Scheduler's SMART Test task (`supervisor/src/scheduler/router.py`), the Storage page's SMART data and the smartctl power reads of an EPC disk and of a host without hdparm (`supervisor/src/storage/disks.py`), and the automatic offline scan's read and switch of an idle timeout (`supervisor/src/storage/spindown.py`). The argument lists, the timeouts and the answers stay as they were.
- **`container_disk_node`** takes a device `/dev/<name>` (a lowercase name of letters and digits, at most 32) and reads the device number of the host's whole disk of that name from `/sys/block/<name>/dev` (`SYS_BLOCK`), which the privileged container sees as the host does: the kernel's block devices are in no namespace. Then, under one lock:
  - a node at `/dev/<name>` (`CONTAINER_DEV`) that is a block device of that number is left as it is: no write, no log line, as for every disk that was there when the container started;
  - a missing one is made, and one with another number, or anything else at that name, replaced: a block device node, mode 0600, made with `os.mknod` under the temporary name `.<name>.unos-new` beside it and renamed over the old entry (`os.replace`), in the container's `/dev`, a tmpfs in RAM that the next start of the container fills afresh. INFO "Made" or "Replaced /dev/<name> in the container as the host's disk <major>:<minor>", once per change;
  - before it writes, it checks that `/dev` is a filesystem of its own, not the host's `/dev` as PID 1 sees it (`HOST_DEV`, `/proc/1/root/dev`, which `pid: host` gives the container; `_dev_is_the_containers` compares their `st_dev`): a bind mount of the host's `/dev`, or a supervisor run on the host itself, gets no node of UNOS's, since the kernel keeps the nodes there;
  - a name of which the host has no whole disk (a partition, a disk that left after lsblk listed it) gets no node, and `run_smartctl` raises `host.NoHostDisk` "The host has no disk <name>" without running smartctl, so that smartctl never opens a node whose number another device may have taken;
  - an OSError of sysfs or of the node (a refused mknod, say) raises `host.DiskNodeError`, of which NoHostDisk is one, without running smartctl, and is logged as a warning once per disk until its node is right again.
- **Left alone:** where host commands run locally (`UNOS_HOST_EXEC=local`: the stand-in and the compose test stack), a device that is not `/dev/<name>`, which smartctl gets as before, and a container without `SYS_BLOCK`.
- **At `/dev/<name>`, nowhere else:** smartctl tells the type of a device from its name (`/dev/sd*` and `/dev/nvme*`, as smartmontools' `os_linux.cpp` does) and finds a USB bridge through `/sys/block/<name>`, so a node in another folder, or the host's node through `/proc/1/root/dev/<name>`, would need `-d` for every disk.
- **No privilege changes.** `deploy/docker-compose.yml` is unchanged: the container is privileged already, so it may make device nodes and open every device; UNOS now makes the nodes it reads. Reading a sysfs attribute and making an inode send the disk nothing, so a sleeping disk stays asleep (ADR-0378).
- **Errors.** For NoHostDisk, `GET /api/v1/health/disk/{device}` and `POST /api/v1/health/disk/{device}/test` answer 400 with its text, as for a disk the host does not list; for another DiskNodeError, 500 "Failed to get SMART data: <reason>" and "smartctl could not run on <device>: <reason>", without a traceback, since the node's warning is logged already. `GET /api/v1/storage/disks/{name}/smart` answers its error answer with the reason, a SMART Test run fails with it, Disk Health's list shows such a disk UNKNOWN, the monitor records no snapshot of it, and the power read is unknown, as for a disk that smartctl cannot open. Other errors of smartctl's start (an OSError of `Popen`) are answered as before.
- **Tests:** `supervisor/tests/test_hot_plugged_smart.py`. Through the API, with `FakeHost`'s model of the container's `/dev` (`attach_disk`, `detach_disk`, `container_dev`, `nodes_made` of `supervisor/tests/test_pool_persistence.py`): a disk attached after the start shows its SMART data on Disk Health and in the list and overview, starts a self-test, runs a SMART Test task, is recorded by the SMART monitor, answers the Storage page's SMART data and the smartctl power reads, and gets its offline scans turned off for an idle timeout; a disk that was there keeps its node, and a second read makes and logs nothing; a node whose number another disk took is replaced before smartctl reads; a disk that left and a partition get no node and no smartctl; a sleeping disk stays asleep; a node that cannot be made answers the errors above with one warning; nothing is made where commands run locally, into a `/dev` that is the host's, or for another path; the name smartctl appears in `src/` only in `run_smartctl` (an AST walk that finds a list over several lines, a tuple or a constant; the fake's smartctl also fails a test that did not ask for the node first). In folders of the test's own: the sysfs read, an entry that is no block device, the number of a block device of the machine's `/dev` (read only), the `st_dev` comparison, the node made under its temporary name and renamed, a failed mknod or rename that leaves the old entry and no temporary, nothing written into a `/dev` on the host's filesystem, and a real block node (skipped unless root on Linux). `supervisor/tests/conftest.py` points `SYS_BLOCK`, `CONTAINER_DEV` and `HOST_DEV` of every test at missing folders, so that no test reads this machine's sysfs or changes its `/dev`.
- **Device check** (by hand, the steps in the entry's notes): the dev device's only disk, `sda`, which was there at the start, keeps Docker's node, and its SMART data, a short self-test's start and the monitor's record work as before, before and after a reboot; a USB disk attached while UNOS runs is the owner's check.

## Consequences

- A disk attached while UNOS runs is read, tested and monitored like one that was there at the start, without a restart; its node stays until the container restarts, which costs nothing (RAM).
- The node of a name is checked against sysfs right before each smartctl: one sysfs read and one lstat, no command. Between that check and smartctl's open, a disk whose number is not its name's, such as an NVMe disk, could leave and another device take its number (an SCSI disk's number follows from its name: the sd driver derives both from one index); smartctl would then read that device once, start its self-test or, for an idle timeout's Save, switch its automatic offline scans (`smartctl -o`). The window is milliseconds and needs a disk to leave and another to appear in it.
- The node is made before `run_in_container` looks for a stuck run of the same command: a disk whose smartctl is still stuck gets its node, and its INFO line, for a run that then does not start.
- A disk smartctl cannot pass through, such as one behind a USB bridge it does not know, still shows UNKNOWN with lsblk's model and size, as when it was there at the start.
- Only smartctl gets nodes. Other commands in the container reach the pools through their mount paths (btrfs) or run on the host (`btrfs filesystem show`, hdparm, wipefs), so nothing else needed them.

## Considered options

- The host's `/dev` in the container, a bind mount `/dev:/dev` in `deploy/docker-compose.yml`: no code, but a change of the container's mounts and a recreate on every host. Docker then leaves out its own mounts below `/dev`, so the container would share the host's `/dev/shm`, `/dev/pts` and `/dev/mqueue`, more of the host than UNOS needs, for the nodes of disks alone.
- smartctl on the host through `host.run_on_host`: no node at all, but the host's `timeout` cannot end a smartctl stuck in the kernel, and `run_on_host`'s limit ends only nsenter, so each smartctl command would need what ADR-0378 built for hdparm (one run per disk, a pgrep before the next) to keep ADR-0290's bounds; the host's smartmontools may be older than the image's (`supervisor/Dockerfile`), and a host set up by hand may lack it.
- A udev rule on the host that makes the node in the container (`docker exec` at each `add` event): a host-level file to install and remove, which runs whether UNOS reads the disk or not and fails while the container is down.
- smartctl given the host's node as `/proc/1/root/dev/<name>`: no write at all, but smartctl does not recognize the type of such a path, so every disk would need its `-d`, which UNOS would have to work out for each USB bridge as smartctl does.
- Removing the container's node of a name the host no longer has: it would touch nodes that nothing reads (a partition's), while not running smartctl for such a name already keeps it from opening a stale node.
