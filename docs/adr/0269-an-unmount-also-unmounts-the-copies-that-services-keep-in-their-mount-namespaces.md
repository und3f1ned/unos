# ADR-0269: An unmount also unmounts the copies of a pool's mount that services keep in mount namespaces of their own, and refuses every other user as before

## Context

On the dev device (Armbian) every Unmount and Remove Pool answered 409 "Pool 'data' is still in use outside the host ..., so it was mounted again", also with every app stopped (storage.mount-and-unmount, storage.forget-pool). systemd runs services with sandboxing (systemd-resolved, -timesyncd, -udevd, -networkd, -logind, rsyslogd) in mount namespaces of their own, and each of them held a copy of the pool's mount, root `/` at `/mnt/pools/data`, in a peer group of its own without a master, so the host's `umount` did not reach it. The filesystem stayed mounted, and the check after the umount (ADR-0070) mounted the pool again, although the services do not use it.

## Decision

- After the host's umount, when `/sys/fs/btrfs/<uuid>` still exists and the filesystem is not mounted elsewhere on the host, `_unmount_pool_target` in `supervisor/src/storage/pools.py` reads the mount table of every other mount namespace of the host: `lsns --json --type mnt --output NS,PID` names one process of each (its lowest PID; PID 1's namespace is the host's), and `findmnt --task <pid>` reads that process's table (`mount_namespace_pids` and `namespace_mounts` in `supervisor/src/storage/disks.py`). A mount of the pool's filesystem is recognised by the device number (MAJ:MIN) that the host's mount showed, which every mount of a btrfs filesystem shows.
- A copy of the host's mount is a mount of that filesystem at the pool's mountpoint with the root that the host's mount had (FSROOT, `/`), in a namespace whose own root is the host's: its mount at `/` shows the filesystem (MAJ:MIN) and the folder (FSROOT) that the host's `/` shows, as in the namespaces that systemd makes for services. Under such a copy lies the host's own mountpoint, which the unmount write-protects (ADR-0034), so a process there that still tries to write to the pool fails as a host process does. Each copy is unmounted in its namespace by the host's umount, `umount --namespace <pid> /mnt/pools/<name>`, which enters the namespace for the unmount alone, so the namespace needs no umount of its own; once for each copy stacked there; never lazily. The supervisor's log names the processes whose copies it unmounted, as a warning, the level its log shows.
- Nothing is unmounted in any namespace, and the pool is mounted again with 409, when a namespace has the filesystem mounted anywhere else (a container's bind mount of a folder, the whole pool at another path, a folder of it at the pool's mountpoint); has it mounted at all while its root is not the host's, also at the pool's mountpoint with the host mount's root; or has another filesystem mounted at the pool's mountpoint together with a copy, such as the cover with which systemd hides a path from a service: an umount by the path removes the topmost mount there, which may be the cover. A container's root is its own (the overlay of its image, or a folder of the host's filesystem), and so is that of a process that a chroot into a folder keeps from seeing any mount at `/`. A container that binds a parent folder of the pool with Docker's default propagation, rprivate (`-v /mnt/pools:/mnt/pools`, or the whole `/mnt`, which the Containers page can make), keeps the pool's mount at its mountpoint, and its apps use the pool there; Docker reports a Source that is not in the pool, which the check before the umount does not count, and when Docker cannot be asked, a container that binds the mountpoint itself looks the same. Unmounting the pool there would leave such apps writing into an empty folder, or into the container's own layer on the system disk. The message names the process: "Pool 'data' is still in use outside the host (process 1200 has it mounted at /downloads), so it was mounted again. Stop the apps and containers that use the pool and try again."
- After the copies, `/sys/fs/btrfs/<uuid>` decides: gone, the unmount succeeds; still there, the pool is mounted again with 409, which names the first copy that stayed ("process 640 keeps a copy of its mount, and unmounting it there failed: umount: /mnt/pools/data: target is busy"), or says "for example by a container's bind mount" as before. After a failed unmount the other copies are still unmounted, and the namespace is read again: a copy that went with the unmount of its peer, or with its exited process, is no failure. A namespace whose table cannot be read is left out; when lsns fails, the pool is mounted again and refused as before.
- `HOST_TOOLS` names `lsns` (util-linux). Unmount and Remove Pool share this code, and their endpoints apply smb.conf after it as after any unmount (ADR-0248). The Unmount and Remove Pool dialogs show the server's message, and the Remove button names its pool for screen readers.
- Tests: `supervisor/tests/test_pool_persistence.py` (TestUnmountAndDelete on the mount namespaces of the FakeHost, TestMountNamespaces, TestPoolEndpoints, and the texts of `webui/tests/storage-fakes.ts`), `supervisor/tests/test_smb_integration.py`, `webui/tests/storage.spec.ts`.

## Consequences

- On a host whose services run sandboxed, a pool unmounts once no app, container, SMB client or open file uses it.
- A refusal can come after some copies were unmounted. Mounting the pool again on the host does not give those services their copies back: until they restart, they see the empty, write-protected mountpoint (ADR-0034). They had no file of the pool open.
- A copy that its namespace hides, below a cover of a parent folder or outside a chroot, is not unmounted or not seen: the unmount is refused, as before. A container that binds `/mnt/pools` or `/mnt` without propagation keeps the unmount refused while it runs, with a message that names its first process, not the container; one that binds them with `rslave` or `rshared`, as the supervisor binds `/mnt`, has no copy left after the host's umount.
- A service run with a root of its own (`RootDirectory=`, `RootImage=`) counts as a container: its copy keeps the unmount refused.
- The pool stays unmounted on the host while the tables are read, one host command per mount namespace in turn, before a refusal mounts it again: the more containers and sandboxed services a host runs, the longer.
- The unmount in a namespace waits 60 seconds like the host's umount, without the host's timeout(1) (storage.commands-time-out-cleanly). The PIDs that lsns names are used within that unmount; a PID is not reused that fast.
- The function assumes one filesystem at the pool's mountpoint, as `_umount` and the sysfs check do.

## Considered options

- `nsenter -t <pid> -m umount <mountpoint>`: it runs the umount of the namespace's own files, which a container may not have.
- A lazy unmount (`umount -l`): the filesystem would stay in use behind it while the pool looked unmounted and its disks safe to remove.
- Unmounting the copies in every namespace, containers included: a running app whose container binds `/mnt/pools` would lose the pool whenever it had no file open at that moment, and the unmount would succeed, where the check after the umount refused it before (ADR-0035, ADR-0070).
- Refusing up front the running containers that bind a parent folder of the pool without propagation: Docker reports only its own containers and only when it answers, so the check of the namespace's root is still needed after the umount, and it covers these containers as well.
- Mounting the pools with shared propagation so that the host's umount reaches the copies: the host's mount is shared already, and the copies sit in peer groups of their own without a master, which no propagation from the host reaches.
