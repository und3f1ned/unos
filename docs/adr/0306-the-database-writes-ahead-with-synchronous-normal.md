# ADR-0306: The database uses SQLite's write-ahead log with synchronous NORMAL, and a power cut can roll back its last commits

## Context

`unos.db` used SQLite's defaults, the rollback journal (DELETE mode) with `synchronous=FULL`, and ADR-0078 accepted that a commit followed closely by a power cut can roll back. On the dev device a sign-in wrote 0.156 to 0.168 MiB to the SD card, mostly the commit of its login-history row (ADR-0224, feature `architecture.sqlite-write-cost`). Counted with a VFS that counts SQLite's own file operations (SQLite 3.54, one such commit): the rollback journal with FULL created `unos.db-journal`, wrote 16.9 KB to it, synced it twice and its folder once, wrote and synced 4 pages of `unos.db` and deleted the journal, and every sync makes ext4 commit its own journal (the device's root file system: `commit=120`). The rollback journal with NORMAL still synced 2 files and the folder, TRUNCATE and PERSIST synced 4 times, the write-ahead log with FULL once, and with NORMAL, in the middle of the log, not at all. Offered the rollback journal as it was, the log with NORMAL and the log with FULL, with the costs below, the owner chose "WAL + NORMAL", and answered "Yes, an exception" for the start's write of `unos.db-shm` (2026-11-08).

## Decision

- Every connection of the app's engine to a database file runs `PRAGMA journal_mode = wal`, and once it is in the log `PRAGMA synchronous = NORMAL` (`write_ahead`, attached by `create_app_engine` in `supervisor/src/database.py`). The journal mode is kept in the file, so other connections, such as the emergency command line's (ADR-0284, synchronous FULL by default), use the log too. A switch that SQLite refuses, on a read-only or full `/data` before the first one, leaves the connection in the rollback journal with FULL, which reads as before (ADR-0251); a warning says why, and a later new connection or the next start tries again. Checkpoints keep SQLite's defaults: automatic when the log reaches 1000 pages, after which `unos.db-wal` is reused from its start, without a size limit.
- At the end of the lifespan, `checkpoint_db()` (`supervisor/src/main.py`) copies the log into `unos.db`, syncs both and empties the log (`PRAGMA wal_checkpoint(TRUNCATE)`), so a stopped supervisor leaves every commit in `unos.db`. The pool stays open: with the last connection SQLite would delete `unos.db-wal` and `unos.db-shm`, and the next start, which would have to make them again, could not read the database on a full or a read-only `/data`.
- Copies of the database stay one file with the rollback journal: `copy_database` in `supervisor/src/backup/router.py` (backups, the scheduler's backup task, the copy kept before a restore) and `backup_database_online` in `deploy/update.sh` switch the copy back with `PRAGMA journal_mode = DELETE`, and a backup's `unos.db` must still have the rollback journal (`_verify_database`). Of a supervisor that is not running, `update.sh` copies the files: `unos.db`, and beside it `unos.db-wal` when the volume has one. A restore refuses a backup whose pages differ in size from the live database's before it changes anything (`_verify_page_size`): SQLite's backup API cannot change the page size of a database in the write-ahead log. `docs/RECOVERY.md` copies the database's files from the read-only mount of a NAS's system disk, as root, and reads the copy.
- The power-cut window is accepted, as in ADR-0078, and the security changes of those seconds with it: a new password, two-factor authentication turned on or off, a used recovery code (which then signs in once more, ADR-0238), a disabled or deleted API token, a deleted or demoted user. The database stays authoritative, and the startup reconcile (ADR-0138) repairs the host from it: the passdb entries of rows that are not active are removed, marked host accounts that no row has are stale and removed (ADR-0108), and the open sessions of accounts that are not active end (ADR-0104). The files UNOS writes next to smb.conf stay durable on their own (`_install` and `_write_file_durably` in `supervisor/src/shares/smb.py`), and `/etc` is synced on the host after every change of its account files (`flush_etc` in `supervisor/src/shares/accounts.py`).
- An exception to ADR-0214's rule that a start that changes nothing writes nothing: the first connection after every start of the supervisor makes `unos.db-shm` again (SQLite empties and refills it), about 0.05 MiB on the system disk (its 32 KB and the file system's metadata), against about 0.1 MiB that the log saves at every commit (a sign-in's commit wrote about 0.14 MiB). ADR-0214 names it, and so does the second start of `test_whole_cycle` in `supervisor/tests/test_smb_integration.py`.
- Tests: `supervisor/tests/test_sqlite_write_cost.py` (the app's engine as the supervisor builds it: both connections in the log with NORMAL, a sign-in's commit leaves `unos.db` alone and appends 3 frames of 4120 bytes; a clean stop leaves every commit in `unos.db` and keeps the log's two files; a refused switch still reads, with FULL), `test_backup_restore.py` (a backup of a database in the log restores with its last commits, a copy is one file with the rollback journal, another page size is refused), `test_deploy_scripts.py` (update.sh's copies of a running and of a stopped supervisor), `test_emergency.py` (`TestRunbook`) and `test_smb_reconcile.py` (`TestRollback`).

## Consequences

- A commit in the middle of the log appends the pages it changed to `unos.db-wal` (a sign-in's row: 3 pages, 12.4 KB), changes 3 pages of `unos.db-shm`, syncs nothing and creates or deletes no file. The commit that starts the log again, the first after a start and the first after each checkpoint, also syncs `unos.db-wal` once. The kernel writes the pages out within about 35 seconds (`dirty_expire_centisecs` 3000 on the device), together with those of other commits. `scripts/dev/sd.sh measure` syncs at its end, so it counts a sign-in's writes at once; the measurement after the deploy takes a second sign-in, in the middle of the log, and a start, against the exception's 0.05 MiB.
- A power cut can roll back the commits of the last 35 seconds once `unos.db-wal` is reused, and of up to about 155 seconds while it grows, as its new blocks and size reach the disk only at ext4's next journal commit (at most 120 seconds after the writeback). It grows for its first 1000 pages after every start, which on a quiet NAS takes days. Several commits can go, where the rollback journal lost at most the last one, within up to 120 seconds (ADR-0078). The log's checksums end it at the last whole commit, so the database itself is not damaged. The audit log's last lines can be lost in the same power cut, as before: its appends are not synced either (ADR-0224).
- A checkpoint, when the log reaches 1000 pages and when the supervisor stops, writes each page that changed since the last one into `unos.db` once and syncs both files.
- `unos.db-wal` and `unos.db-shm` (32 KB) stay beside `unos.db` in `/data`, also while the supervisor is stopped. The log holds up to about 1000 pages (4 MB), and after a restore, which writes the whole database into it in one transaction, about the database's size, until the supervisor stops. A copy of the data volume takes the three together, as `scripts/dev/deploy.sh backup` and update.sh's `data.tar.gz` do.
- Whatever is put back as `unos.db` by hand, with the supervisor stopped, the `unos.db-wal` and `unos.db-shm` beside it are deleted first or replaced by the copy's own: SQLite applies a log it finds beside a database file, whatever that file's header says, so a backup put back beside a newer log reads that log's pages (`docs/INSTALL.md`). The in-app updater's copies of `unos.db` do not yet (`system.in-app-updater`).
- Where SQLite may not write, it reads a database in the log only with `unos.db-wal` and `unos.db-shm` beside it. The stop keeps them, so a supervisor that starts on a read-only `/data` (ext4's `errors=remount-ro`) still reads its database, but not once they are deleted.
- Readers no longer wait for a writer, and a commit no longer waits for readers.

## Considered options

- The write-ahead log with synchronous FULL: every commit is durable when it returns, at one sync per commit, which makes ext4 commit its journal each time, and without the writes of several commits going out together.
- Synchronous FULL only for the security changes above, and NORMAL for the rest: offered, and not chosen by the owner.
- Closing the pool when the supervisor stops: SQLite then deletes `unos.db-wal` and `unos.db-shm`, and the next start, which must make them again, cannot read the database on a full or read-only `/data`.
- The rollback journal with synchronous NORMAL, TRUNCATE or PERSIST: two to four syncs per commit remain.
- The write-ahead log with `locking_mode=EXCLUSIVE`, which keeps `unos.db-shm` in memory: one connection would lock out the pool's others, the emergency command line and the backups' copies.
