# ADR-0383: An app's install runs as a background job whose progress the App Store shows

## Context

ADR-0381 kept the install of an app one request that answered after its pulls: Immich's four images took 299 s on the dev device, during which the App Store showed only a spinner, a browser could give up on the request, and nothing said how far the pulls had come. The ledger entry `apps.install-progress` asks that `POST /api/v1/apps/install` answer at once with a job, that the checks, pulls, creates and starts run in the background, and that the App Store show each image's pull, each container's start and the result, also after a reload. The owner delegated the choices, asking above all that it be safe. This ADR supersedes only the part of ADR-0381 that made the install one request and named `scripts/dev/api.py --timeout 3600` for it; every other rule of ADR-0381 (the model, the identity, the password on the pool, the pinned images, the checks before the first pull and their order, the readiness waits, the clean-up of a failed install, the system disk, Immich) stays in force as written there.

## Decision

- **The request.** `POST /api/v1/apps/install` answers 202 at once with the job (`AppInstallJob` of `supervisor/src/apps/schemas.py`), running, at the step `checking`. Before it starts the job it answers only what reads neither Docker, the host nor the pools: 422 for a body it does not take, 404 for an app that the catalog lacks, 400 for a request that the template refuses (the group option, a host port outside 1 to 65535, given twice or moved in the host's network, a variable that UNOS sets, a missing or placeholder value: `_check_request` of `supervisor/src/apps/router.py`), and 409 while an install runs or another change of the app is under way. Every other check of ADR-0381 (the pool, the folders and the share folders, the password files, the app's names and network in Docker, the host ports in use, the system disk's free space, the hardware) runs in the job, in ADR-0381's order and before any pull; a refusal ends the job `failed` with the detail and the HTTP status that the request answered before (`error`, `error_status`). The App Store keeps its details dialog open while the job checks, so that such a refusal still shows where the request was made.
- **One install at a time.** A second install while one runs, of the same app or of another, answers 409 ("Immich is being installed already: wait for the end of its install", "An install of Immich is under way: install Jellyfin once it has ended") and starts nothing. The checks of the free space and of the ports hold only against what is there before the pulls: two installs at once would each pass them against the same free space and the same ports. The job holds the app's lock (`stacks.acquire`, the lock of `stacks.app_lock`) from the request to its end, so that a start, stop, restart or uninstall of the app answers 409 meanwhile.
- **The job runs in a thread of its own** (`supervisor/src/apps/install_jobs.py`): a daemon thread, not the event loop and not its executor, which a pull of minutes would hold (ADR-0254, ADR-0021). The install keeps ADR-0254's rule that a pull has no deadline; a pull that never ends holds the one install until it ends or the supervisor restarts.
- **Its state is kept in RAM only.** `install_jobs` keeps the running job and the last job of each app since the supervisor started, by the app's id: a new install of an app replaces its last job, and `DELETE /api/v1/apps/install/jobs/{id}` (204) forgets an ended one, as the App Store's Dismiss does (409 for the running job, 404 for one that is not kept). Every new state of a job is a new object in memory; no progress is written anywhere, so the system disk (the dev device's SD card, ADR-0214) gets only what the install itself writes: the images, the container records, the pool's folders and password file, and one audit entry.
- **What it reports.** `step`: `checking`, `pulling`, `creating` (the pool's folders, the network, the containers), `starting`. `images`: each image once, in the order of the containers that run it, listed once the checks passed: `waiting`, `present` (a pinned image that Docker has, not pulled), `pulling`, `pulled` or `failed`, with `layers` (the layers that Docker's pull stream named so far), `layers_done` ("Pull complete" or "Already exists"), `bytes_total` (the download sizes of the layers that Docker reported so far) and `bytes_done`. `containers`: each container in its start order, `waiting`, `created`, `starting` (for a companion of `depends_on`, until it is ready), `running`, or, after a failure, `failed` (the one whose create, start or readiness failed) and `removed` (by the clean-up). The end: `succeeded` with `result`, the `AppInstallResponse` that the request answered before, or `failed` with `error` and `error_status`; `finished_at` either way.
- **The pull stream.** The install pulls with docker-py's `client.api.pull(..., stream=True, decode=True)` and reads the stream to its end in the job's thread, each line into the job's counts; a line with an error fails the pull, which answers ADR-0381's "Failed to pull image ...". The counts are published at most once a second (`PROGRESS_INTERVAL_SECONDS`), a change of state at once. A pinned image is still pulled by its digest and tagged afterwards (ADR-0381).
- **How the App Store learns it.** `/ws/v1/events` sends administrators `{"type": "app_installs", "data": [...]}`, the jobs as `GET /api/v1/apps/install/jobs` answers them, after `auth_ok` once there is a job and whenever they change, at most every 2 seconds like its other messages (`supervisor/src/websocket/events.py`); regular users never get it. The web UI keeps them in the store `appInstalls` (`webui/src/lib/stores/appInstalls.ts`), which `auth_ok` empties, so that after a restart of the supervisor, which forgot its jobs, no install shows as running. A reload of the App Store signs in to the socket again and gets the jobs back: the running install with its progress, and the result of the last ones. The App Store shows a card per job above its tabs (`webui/src/lib/components/apps/AppInstallJobs.svelte`): each image's state, its layers and a bar of its bytes, each container's state, and the end, the install's notices or the failure, with Dismiss once it ended; it reads the installed apps again when a job ends. Nothing polls (ADR-0365).
- **For scripts.** `GET /api/v1/apps/install/jobs` lists the jobs, and `GET /api/v1/apps/install/jobs/{id}?wait=SECONDS` (0 to 3600) answers the job once it has ended or the seconds have passed, looking at it in memory every half second without holding a thread or a database session (it closes the one that checked the credentials first, so that no read transaction holds back the database's checkpoints, ADR-0306). A device check waits for an install with `scripts/dev/api.py POST /apps/install -` (202 with the job's `id`), then `scripts/dev/api.py --timeout 3660 GET /apps/install/jobs/<id> --param wait=3600`, which replaces ADR-0381's `--timeout 3600 POST`.
- **A stop of the supervisor** asks the running job to stop and waits up to 5 seconds for its end (`install_jobs.stop_for_shutdown`, beside the repair's stop in the lifespan of `supervisor/src/main.py`, both within Docker's 10 s before it kills the container). The install looks for the stop at each line of a pull, before it writes to the pool, before the network and each create and start, and at each look while it waits for a companion (`stacks.wait_ready`'s `check`). Before any container is made, the job ends `failed` with 503 and nothing in Docker: the images pulled so far stay, and so do the folders and the password file if they were made, as after any failure of ADR-0381. Once it made a container or the network, it leaves what it made as it is, not stopped and not removed, since a forced removal would kill a database halfway through its first start, and writes `app_installed` with success false naming what was left behind. The restarted supervisor knows no job: the app is then listed as installed, stopped or incomplete, and its Start (with ADR-0381's waits) or Uninstall goes on from there. A kill or a power cut leaves the same without an audit entry; a pull cut off with the supervisor's connection ends in Docker.
- **The audit log** keeps ADR-0350's rule and ADR-0381's texts: one `app_installed` per job, written by the job's thread before its end is published, with the administrator and the client of the request: success when it installed, success false when the clean-up of a failure or a stop of the supervisor left something behind, and nothing when its checks refused it or its clean-up removed everything. Starting a job and dismissing one are not audited: neither changes the NAS.
- **Roles.** The install and the job routes are for administrators only (the apps router is in `_ADMIN_ONLY` of `supervisor/src/main.py`, and each route requires an administrator, ADR-0030), and so is the socket's message: a job names an app's folders on the pools.
- **Tests.** `supervisor/tests/test_app_install_jobs.py` (the 202 at once, the answers before the job, one install at a time, the app's lock, the pull's layers and bytes, the containers' states and steps, the end and its audit entry, a refusal of the checks, an error in a pull's stream, a failed start, the listing, dismissing and waiting, a stop of the supervisor before and after a container was made, the roles), `supervisor/tests/test_ws_auth.py` (`TestTheInstallsOnTheEventsSocket`); the install tests of `test_apps.py`, `test_app_stacks.py` and `test_audit_storage_and_apps.py` read the job's end through `install` of `test_apps.py`, against the pull stream of `supervisor/tests/docker_fake.py`; `webui/tests/apps-install-progress.spec.ts` on the stand-in, with the jobs on a fake events socket (`fakeInstallEvents` of `webui/tests/apps-fakes.ts`), and the job API of the stand-in itself in `webui/tests/api.spec.ts`.

## Consequences

- A user can leave the App Store, or reload it, while Immich downloads, and sees how far each image has come; a browser no longer waits minutes for one request.
- A refusal that only the checks find (a port in use, too little space, a share's folder) comes a moment after the click, from the job, instead of in the answer; the dialog still shows it.
- Only one app installs at a time; a pull that never ends blocks the next install until the supervisor restarts.
- A restart during an install can leave an app installed but not started, or incomplete; the Installed tab shows it, and Start or Uninstall handles it. The App Store does not show the last result of an install across a restart.
- Scripts and device checks that installed with one request and `--timeout 3600` now need the waiting GET.

## Considered options

- Keeping the cheap checks of the pool, the ports and the free space in the request, with their 4xx: they read the host and Docker, which can take seconds or 60 s when Docker hangs (ADR-0254), against "answers at once"; the dialog that waits for the checks keeps their messages where they were.
- Installs of several apps at once, with checks that count the pulls of the other jobs: more code for the rare case of two installs, while one at a time keeps the space and port checks true.
- Keeping the jobs in the database, to show them after a restart: a write per state on the SD card for a result that the Installed tab and the audit log already give.
- Rolling back what an install made when the supervisor stops: the database's stop timeout (60 s) does not fit in Docker's 10 s, and a removal cut off halfway would leave less than the stop does.
- A page that polls `GET /apps/install/jobs/{id}`: ruled out by ADR-0365; the events socket already reaches every administrator's page.
