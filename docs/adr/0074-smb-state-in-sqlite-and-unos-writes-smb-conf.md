# ADR-0074: Shares and SMB accounts live in SQLite, and UNOS alone writes smb.conf

## Context

Before slice 2, a share existed only as a section of `/etc/samba/smb.conf`, and UNOS users had no Samba accounts (ADR-0059). Per-user access, the startup reconcile and backup and restore need one state that the host can be compared with, and every rule about what may reach smb.conf needs one place where it is enforced.

## Decision

- Shares, their per-user access, the SMB accounts and the installation-wide SMB state are four SQLite tables in `unos.db`: `smb_shares`, `smb_share_access`, `smb_accounts` and `smb_state` (`supervisor/src/shares/models.py`).
- `/etc/samba/smb.conf` is generated entirely from these rows: the header `# Generated by UNOS from its database. ...`, a hardened `[global]` (ADR-0087) and one fail-safe section per served share (ADR-0088), rendered by `render_config` in `supervisor/src/shares/smbconf.py` and installed by `apply_smb_config` in `supervisor/src/shares/service.py` (ADR-0089).
- A hand edit of smb.conf is overwritten by the next apply; the file says so in its header. Shares that already exist in a file UNOS did not write are imported once (ADR-0084).
- Every value is validated again when the file is rendered, because a restored database is untrusted input (ADR-0144).

## Consequences

- Every backup carries the shares, their access and the SMB account state (uid, allowed, password state) inside `unos.db`.
- The startup reconcile can repair the host from the database (ADR-0078, ADR-0138).
- Samba settings that UNOS does not render cannot be kept by editing smb.conf: they need a change in UNOS (for example ADR-0161).

## Considered options

- Keeping share definitions in smb.conf as before: not taken; such shares are imported once instead.
