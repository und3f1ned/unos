# ADR-0388: Each container of an app gets its own memory and CPU limits, kept by Docker and for the next install, and its use is read from its cgroup and alerted

## Context

The ledger entry `apps.container-resource-limits` asks that an administrator set a memory limit and a CPU quota for an app, which `docker inspect` shows, and that the app's page show its use against the limits, crossing one sending an alert; `apps.compose-stacks` left Immich's limits to it (ADR-0381: "limits belong to `apps.container-resource-limits`"), and its device check measured Immich idle on the dev device (8 GB, 8 CPUs): the server 577 MiB, the machine learning 145 MiB, Valkey 6 MiB, Postgres 70 MiB, its peaks under Immich's jobs not yet. The owner delegated the choices, asking above all that it be safe. UNOS keeps its idle load within its budget (ADR-0374), lets the pools' disks sleep (ADR-0378), writes nothing periodically to the system disk (ADR-0214), and alters no table (ADR-0319).

## Decision

- **Per container.** Each container of an app has its own limits: Immich's server, database, Valkey and machine learning each one. The kernel holds each container's cgroup to its own limits, and the containers' needs differ (the machine learning's models against the database's cache); one limit for the app would need a parent cgroup per app (Docker's `CgroupParent` with a systemd slice of the host) and would let one container's peak starve the others. The Installed tab shows them per app.
- **Applied by Docker and kept in two places.** `PUT /api/v1/apps/installed/{container}/limits` (the container's id or Docker name; any container of an app) with `memory_limit` (bytes) and `cpu_limit` (CPUs), both required (422 without one, so that a field left out never removes a limit) and null for none, sends docker-py's `Container.update` (`mem_limit` and `memswap_limit` the same, `cpu_period` 100000 and `cpu_quota`), which changes a running container's cgroup at once and its HostConfig, where `docker inspect` shows `Memory`, `MemorySwap`, `CpuPeriod` and `CpuQuota`, for every later start: a restart, a stop and start, Docker's restart policy and a reboot keep them. The new table `app_resource_limits` (`supervisor/src/apps/models.py`: app, container name, `memory_bytes`, `cpu_quota`) keeps them for the app's next install, which creates each container with its own (`create_args` in `_create_options` of `supervisor/src/apps/router.py`) and names them in its audit entry; an uninstall keeps the rows, as it keeps the data folders (ADR-0256), so a reinstall has them again. After the update the container is read again: what Docker keeps is what counts, and a limit that it discarded with a warning (a kernel without the memory or CPU controller) answers 409 with Docker's warning, while what it did apply is kept and audited. A row is written only when it differs from what Docker keeps and goes when both limits go. The listing shows what Docker keeps (`limits.in_force`); a restore brings the backup's rows, which the next install applies, while the containers keep Docker's until they are set again. A row whose value is out of this host's bounds (a restored backup of another host) is left out of the install with a warning in the log. The CPU limit is a quota per period, not NanoCpus: docker-py's update has no NanoCpus, and Docker refuses a quota beside them and cannot take them off; a container given `--cpus` by hand keeps that CPU limit, which the listing shows, and a change of its CPU limit answers 409 that says so.
- **Values** (`supervisor/src/apps/limits.py`). Memory from `MEMORY_FLOOR` (64 MiB; the catalog's apps cannot start below it, Docker's own floor is 6 MB) to below the host's memory (MemTotal, `psutil`), and, when it sets or lowers the limit of a running container, at least what that uses now (memory.current without inactive_file, plus memory.swap.current, whose pages come back into its memory) with a margin of 10%, at least 32 MiB (`usage.memory_floor`): a lower one answers 409 ("immich-database uses 300 MiB now: a memory limit below 332 MiB would make the kernel take memory from it or end its processes at once. Set at least 332 MiB, or stop Immich first."), since the kernel would reclaim the pages it works with, its own code among them, and then kill. When the container's cgroup cannot be read, the floor is unknown and the change answers 409 ("stop Immich first, then set it") instead of being sent blind; raising or removing a limit, a CPU limit and a stopped container need no floor. `MemorySwap` equals the limit: no swap beyond it. CPU from `CPU_FLOOR` (0.1) to the host's CPUs, in hundredths. Out of bounds answers 400; another change of the app under way (an install job, a start) 409. No limit is the default, and the catalog sets none until Immich's peaks are measured. A null removes a limit: the CPU quota becomes -1 (none); Docker cannot take a memory limit off an existing container (its update takes 0 as unchanged and refuses less than 6 MB), so the limit becomes twice the host's memory (`NO_MEMORY_LIMIT`), which the container cannot reach, also after a kernel update that changes MemTotal a little, with `MemorySwap` -1 again, and a limit of the host's memory or more (a MiB less in the kernel's memory.max, which keeps whole pages) counts as none everywhere. `GET /api/v1/apps/limits` answers the bounds.
- **Reading the use** (`supervisor/src/apps/usage.py`). Every `SAMPLE_SECONDS` (30) one pass, started in the lifespan of `supervisor/src/main.py` (ADR-0043), asks Docker for the summary list of the running containers labelled `unos.app` (`api.containers`, one request, no inspect per container) and for its `oom` events of them since the last pass (`events` with `since` and `until`, answered from dockerd's memory and closed), and reads six files of each container's cgroup v2 in the host's tree, reached through the root of the host's PID 1 (`/proc/1/root/sys/fs/cgroup`; the supervisor's own `/sys/fs/cgroup` is its container's): `system.slice/docker-<id>.scope` (Docker's systemd driver) or `docker/<id>` (cgroupfs): memory.current, memory.stat (`inactive_file`), memory.max, memory.swap.current (where the kernel counts swap), cpu.stat (`usage_usec`) and cpu.max. These are counters in the kernel's memory, read without a process or a disk: nothing wakes a sleeping disk, and nothing is written; the use and the problems stay in RAM. A cgroup without the CPU controller still shows its memory. The events are asked for from the end of the last query on (a clock set back asks from its new time), the events of the second that two queries share counted once; docker-py sends that query without a timeout, so a pass that waits for Docker longer than `PASS_TIMEOUT_SECONDS` (120) is left to end in its thread, logged once, and no other pass starts meanwhile. Not Docker's stats: a request per container that waits for two of dockerd's reads and makes it compute the whole stats, which costs CPU on a slow board (ADR-0374). The memory used is memory.current without the inactive page cache, as `docker stats` counts it; the CPU used is the CPU time between two passes, in CPUs. `GET /api/v1/apps/installed` answers each container's `resources`: `memory_limit`, `cpu_limit` (Docker's), `memory_used`, `cpu_used` and `sampled_at` (the last pass), none for a container that does not run. A host without cgroup v2 shows no use; its limits still work.
- **Crossing and the alerts.** Problems of the source `apps` (ADR-0332), alerted once each when found, kept in RAM: `app_memory:<container>`, a warning, from a pass that finds the memory used at 90% of the limit or more, until one finds it below 80%; `app_cpu:<container>`, a warning, when the CPU used over the last 5 minutes (`CPU_WINDOW_SECONDS`) averaged 90% of the CPU limit, until it falls below 70% (the kernel holds such a container back); `app_oom:<container>`, an error, from Docker's `oom` event, which containerd sends for each process that the kernel ends in the container's cgroup for lack of memory, also when that ends the container and Docker starts it again with a new cgroup that counts nothing (a poll of memory.events would miss it), kept until an hour after the last kill (`OOM_HOLD_SECONDS`) so that a container that is killed again and again is alerted once; its text names the limit, or the NAS's memory when the container had none. A container that stops loses its memory and CPU problems; one whose cgroup cannot be read keeps them; a pass that Docker does not answer changes nothing and is logged once. The texts of the banner are the web UI's (`problems.kind.app_memory`, `app_cpu`, `app_oom`).
- **Roles and the audit log.** The routes are in the apps router, for administrators only (`_ADMIN_ONLY` and `require_admin`, ADR-0030), and the problems reach administrators only. A change that Docker made writes `app_limits_changed` (resource `container`) with what changed ("Changed the limits of immich-database of the app immich: memory from none to 512 MiB; CPU from none to 1.5 CPUs"), nothing for a request that changed nothing; when the database cannot keep a change that Docker made, the request answers 500 saying that the limits are in force, and the entry is written as failed (ADR-0350).
- **The page.** Each card of the Installed tab lists the app's containers with their use against their limits (`webui/src/lib/components/apps/AppResources.svelte`: the memory and the CPUs, a bar against each limit) and a **Limits** button that opens `AppLimitsDialog.svelte` (memory in MB and CPUs, an empty field for none, the bounds and the use now in its hints, the server's refusal shown as it comes). The page reads the use with the installed list, when it loads and after a change; nothing polls (ADR-0365).
- **Tests.** `supervisor/tests/test_app_limits.py` (the update and what `docker inspect` then holds, the removal, the bounds, the fields left out, the floor with its margin and the swap, a cgroup that cannot be read, NanoCpus, Docker's refusal and its discarded limits, a database that cannot keep them, the roles, the audit entries, the reinstall with the kept limits and a row out of bounds, the use from fake cgroup files, both drivers, the alerts and their clearing, the OOM events across passes, a clock set back, a pass that waits for Docker, Docker or a cgroup that cannot be read), the fake's update, summary list and events in `supervisor/tests/docker_fake.py`, the loop in `supervisor/tests/test_lifespan.py`, `webui/tests/apps-limits.spec.ts` and the dialog's view in `webui/tests/mobile-layout.spec.ts`.

## Consequences

- The limits survive a restart, a reboot, an update of UNOS and a reinstall; after a restore of the database the stored ones can differ from Docker's until they are set again or the app is installed again.
- A pass every 30 seconds costs two Docker requests and six small file reads per running container of an app; with no app installed, one empty list and one empty events query. Nothing is written by it; a change of the limits writes the container's configuration in Docker's data root (on the dev device's SD card), a row of the database and a line of the audit log.
- A memory limit that was removed shows in `docker inspect` as the host's memory, not 0.
- The use on the page is up to 30 seconds old and does not move while the page is open; the alerts do not depend on an open page.
- An OOM kill that happened while the supervisor was stopped is not alerted; one in a container of an app without a limit is alerted too, as the NAS ran out of memory.
- The memory used counts the active page cache, as `docker stats` does: a container that reads much, such as a database, can be warned at 90% of its limit while the kernel could still drop some of that cache.
- A memory limit cannot be set or lowered on a running container whose cgroup UNOS cannot read (a host without cgroup v2, or a cgroup of another layout): the app is stopped first. Docker may keep a running container without swap after its limit was removed until its next start; the device check reads memory.swap.max.

## Considered options

- One limit per app through a parent cgroup: a host-level slice per app, and the containers of an app competing inside it.
- Limits only in Docker's HostConfig: lost at an uninstall and a reinstall.
- Docker's stats stream or `docker stats` for the use: more CPU per read on a slow board than reading the cgroup files.
- memory.events' `oom_kill` instead of Docker's events: misses the kill that ends a container which Docker starts again before the next pass.
- Recreating a container to remove its memory limit: a removal of the container with its whole configuration rebuilt, against a limit that the container cannot reach.
- Limits in the catalog by default: no peaks of Immich's jobs are measured yet (PROGRESS.md, Open owner actions), and a wrong default would kill an app.
