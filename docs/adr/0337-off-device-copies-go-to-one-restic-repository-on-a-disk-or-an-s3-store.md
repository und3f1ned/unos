# ADR-0337: Off-device copies go to one restic repository on a disk or an S3 store, and each copy is checked and its restore tested

## Context

Configuration backups live in `/data/backups` on the system disk, the dev device's SD card, which wears out, and the pools' data has no copy at all: one failed disk loses the configuration or the data (ADR-0041, `backup.off-device-copies`). ADR-0041 proposed a slice that would design btrfs send/receive to a USB disk or a second NAS and restic or rclone to the cloud. The agent decided this slice under the owner's standing instruction, "work on the features, ask no questions; I allow everything", with the goal "a safe, working MVP as soon as possible" (both in translation).

## Decision

- **restic**, Debian's package (0.18 in trixie, the base of `python:3.11-slim`), in `supervisor/Dockerfile` in a layer of its own after the pip layer, so that the apt-get and pip layers stay cached and a device downloads only restic. restic encrypts (AES-256 and Poly1305, scrypt for the password), deduplicates, keeps versioned snapshots, checks a share of the data, limits its bandwidth and writes to a folder or an S3 store. `supervisor/Dockerfile.test` has no restic: the test stack never runs it (below).
- **One copy target per installation, the copy repository** (`supervisor/src/offsite/service.py`):
  - `disk`: a folder strictly below `MOUNTS_BASE` (`/mnt`), absolute, normalized, without `..`, `.snapshots`, `.unos-trash` or the characters `*?[\` (it may become a pattern of `--exclude`), opened component by component without following symbolic links (`open_dir_nofollow`). Refused when it is on the system disk (`on_system_disk`): on the filesystem of `/mnt` (the root filesystem: a disk that is not mounted leaves its empty mount point there) or of the data volume `/data`, or on one of the whole disks under them, as another partition of the system disk is; when UNOS cannot find the whole disks under it or under either of `/mnt` and `/data` (sysfs that cannot be read, a network filesystem, ZFS, an overlay root), with 400 "UNOS cannot tell which disk holds <folder> ...", which is logged too, since the rule cannot be kept then; and when it holds a folder that it copies. Saving makes the folder (0700) when only it is missing and its parent is not on the system disk, and answers 400 with the reason when it cannot be made; a folder that holds files but no repository is refused.
  - The whole disks under a filesystem come from sysfs: its device number (`/sys/dev/block/<major>:<minor>`), and for btrfs, whose every subvolume has a device number of its own, all devices of the filesystem (`/sys/fs/btrfs/<fsid>/devices`, the fsid from the ioctl `BTRFS_IOC_FS_INFO`); a filesystem without a device number of its own (FUSE) by the source of its mount in `/proc/self/mountinfo`. A partition maps to the disks of its device, so that a partition of an md or device-mapper device (`md0p1`) follows to that device and on, and a device-mapper or md device to the disks below it (`slaves`). A loop device counts as a disk of its own, though its file lies on some other filesystem: UNOS sets up none. The system disks are those of `/mnt` and `/data`. The warning that a copy is on a disk it copies (`same_disk`) compares the whole disks too, and the filesystems where the disks of one are not known (a network filesystem).
  - `s3`: an endpoint `https://` or `http://` with a host and port only (restic encrypts and authenticates every file, and SigV4 never sends the secret key), a bucket, an optional prefix and region, an access key ID and a secret access key.
  - SFTP and a REST server are left for later entries (`backup.off-device-copies-over-sftp`).
- **Settings and secrets.** `/data/offsite.json` holds the kind, the target without secrets, the sources, the limits (`limit_upload_kib`, `limit_download_kib`, KiB/s, 0 none, s3 only), the retention (`keep_daily` 7, `keep_weekly` 4, `keep_monthly` 12, at least one above 0) and `check_percent` (2, 0 to 100). `/data/offsite_secrets.json` holds the repository's password (at least 12 characters, typed twice on the page) and the S3 secret key, mode 0600. Both are written in a worker thread as new files renamed over the old ones, the secrets first, synced with their folder; a file that cannot be read is kept as `.bad` with a warning (ADR-0324). Neither is in the configuration backups (only `_FILE_MEMBERS` are). No answer holds a secret: they say `has_password` and `has_s3_secret_access_key`. An edit of the same repository keeps the stored password, and of the same endpoint and access key ID the stored secret key; a new repository needs a new password, and changing the password of one is not part of this decision.
- **restic's process** (`supervisor/src/offsite/restic.py`): an asyncio subprocess off the event loop, `nice -n 10 ionice -c 2 -n 7 restic ...`, in a UTS namespace of its own (below), in a process group of its own that is ended at its timeout and at the end of the lifespan (`offsite.service.stop`): SIGTERM first, on which restic removes its lock and ends, and SIGKILL for what is left 5 seconds later, within the 10 seconds of Docker's stop; with a host name of its own per process (below), a lock that a killed restic leaves is stale for the next restic's `unlock` only after 30 minutes. Its environment is built for it, never the supervisor's (which holds `UNOS_JWT_SECRET`): `PATH`, `HOME` and `TMPDIR` (the tmpfs `/tmp`), `RESTIC_REPOSITORY` (`local:<folder>` or `s3:<endpoint>/<bucket>[/<prefix>]`), `RESTIC_PASSWORD` and, for s3, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_DEFAULT_REGION`. Secrets are never in its arguments (ADR-0125), and both secrets are cut out of its messages before an answer, a status or a log line gets them. Timeouts: cat config and init of Save 120 seconds, which its request waits for (then 400, "The store did not answer within 120 s"), unlock and snapshots 10 minutes, dump 1 hour, check 6 hours, backup, forget with prune and restore 7 days. Cache: `--cache-dir /tmp/restic-cache` for s3, rebuilt after a restart, `--no-cache` for a disk. The cache lives in `/tmp`, the tmpfs in RAM, and counts against its 2 GiB (ADR-0171). `check` runs with `--no-cache` for both kinds: with a cache (`--with-cache`) it would read the index, snapshot and tree files of a warm cache instead of the store, and a damaged copy in the store would pass; without one it reads them all from the store and writes nothing into the tmpfs.
- **Saving tests the target** (`PUT /api/v1/offsite/settings`): `restic cat config` opens an existing repository with the password; exit status 10 (no repository) makes one with `restic init`, the only place that does; 12 (wrong password) and any other failure answer 400 with restic's message.
- **An S3 store must answer first.** restic 0.18 retries a store that does not answer for many minutes, and the device check of Save with `https://127.0.0.1:9` held the request and the lock of the module for the whole 10 minutes of the old timeout. So Save and a run, before restic runs for an s3 store, connect to the endpoint's host and port, and for https make the TLS handshake that verifies its certificate with the system's roots, as restic does, within 10 seconds, sending no request and no key (`probe_store`): a store that does not answer is refused at once, Save with 400 ("The S3 store does not answer at https://127.0.0.1:9: Connection refused"), a run as failed at the step settings. The listing of the snapshots and the restores do not connect first.
- **The folders stay mounted while restic uses them.** restic 0.18's local back end makes the folders that it misses: after an unmount of the target's disk during a run, it would write the rest onto the empty mount point, on the system disk. So the supervisor holds the target, every folder that a copy reads and the new folder of a restore open (the descriptors of the checks, opened without following symbolic links) from the check to the end of the copy or restore, and of the test of Save, and a plain `umount` of their disks fails as busy (`/mnt` is rshared, so the host's unmount meets the container's descriptors). UNOS's own Unmount and Remove Pool (the Storage page) refuse with 409, "Pool '<name>' is used by the off-device copy: the copy started at <time> UTC is still running. Wait for it to end and try again.", while a copy or a restore uses the pool (the target's pool, the sources' pools, a restore's pool), as they refuse for containers; Delete Volume refuses alike, "Volume '<name>' is used by the off-device copy: ...", for a volume that is the target, a folder that a copy reads or a restore's folder, or holds one (a folder above it, such as the whole pool, does not count, as for its other users). Delete Volume checks and deletes under `FOLDERS_LOCK`, the lock under which a copy, a restore or Save names its folders and opens them: either the deletion sees the copy, or the copy finds the volume gone. No code of UNOS unmounts lazily (`umount -l`), which would let the writes go on.
- **One copy repository serves one installation.** Each restic runs in a UTS namespace of its own (`unshare --uts`, which the privileged container may), whose host name, `unos-` and 12 random hexadecimal digits, a small Python step (run with `-B`: no `.pyc` file in the container's writable layer) writes into its `/proc/sys/kernel/hostname` before it executes nice, ionice and restic, its arguments and environment otherwise unchanged. restic 0.18 tests a lock that names its own host name by sending SIGHUP to the lock's process ID: with `pid: host` that ID can be any process of the host after a crash, a power cut say, and every installation would be the host `unos`. With a name that no other restic has, restic never signals a process to test a lock, and a lock is stale only after 30 minutes. A repository that two installations share would have their locks and snapshots mixed: it is not supported, and the guide says so. The snapshots name the host `unos` (below).
- **Locks.** `restic snapshots --json --no-lock`: a listing takes no lock, so that it neither waits nor fails beside a copy or another program. Every step of a copy and of the restores runs with `--retry-lock 10m` (restic 0.16 and later): `forget` and `check` lock the repository exclusively and failed at once (exit status 11) beside any other lock; they wait for it up to 10 minutes now. Saving the settings does not wait (`cat config`, `init`).
- **A copy** (`run_copy`), for the Scheduler's new task type `offsite_copy` (no fields of its own) and for Run now (`POST /api/v1/offsite/run`, 202, in the background):
  1. the settings and the folders: the target as above, without making anything, and each source inside the pools' base (`validate_pools_path`), present and not on the system disk, so that a pool that is not mounted fails the run instead of copying its empty mount point;
  2. `restic unlock` (stale locks only);
  3. the archive of Create Backup (`backup.router.configuration_archive`, built in memory and let go once this step has sent it) through `restic backup --stdin --stdin-filename unos-configuration.tar.gz --tag unos-configuration`;
  4. `restic backup --tag unos-data` of the sources, without `<pools>/*/.snapshots`, `<pools>/*/.unos-trash`, the same one level down (the volumes) and a disk target inside a source;
  5. one `restic forget --tag unos-configuration --tag unos-data` with the retention and `--prune` (restic groups by host and paths, so each kind keeps its own snapshots);
  6. `restic check --read-data-subset=<check_percent>%` (without it at 0);
  7. the restore test: `restic dump` of the new configuration snapshot into TMPDIR, its SHA-256 compared with the archive sent, and the archive checked as an upload is (`backup.router.check_archive`); nothing is restored.

  Both backups name the host `unos` (`--host unos`), whatever the container's hostname is (`${HOSTNAME:-unos}` in compose), so that `forget` keeps one group of snapshots per kind. The first step that fails ends the run, and the run fails, with one exception: exit status 3 of the data's backup, which saved the snapshot without the files that restic could not read. The snapshot and its summary are kept, the other steps run, and the end judges restic's JSON errors on its standard error (`message_type` error, `during` archival, the file as `item` and why): files that vanished while it ran (no such file or directory) are a note of the result and of the Scheduler's record, "N files vanished during the copy: <paths>", and no failure: restic 0.18 leaves out a file that vanished between the listing of its folder and its first open without a word (`filterNotExist`), so only one that vanishes between that open and the next is reported; any other reason (permission denied, an I/O error) fails the run once every step has run, with the step `data` and "N files could not be read: <path> (<reason>), ..., and M more", naming up to 5 (the record: "The copy of the data is incomplete: ..."). An exit status 3 without such an error fails the same way with the end of restic's standard error; the configuration's backup from standard input has no files to miss, and its exit status 3 is a failure. The result is the one write of `/data/offsite_status.json` per run (start, end, trigger, success, the step that failed with its error, the note, the files new, changed and unmodified, the bytes added, the snapshot IDs, the check and the restore test), besides the Scheduler's record; a failed `offsite_copy` task is a task problem and reaches every channel (ADR-0332). A stop of the supervisor during a run records it as stopped.
- **Run now of a task** (`POST /api/v1/scheduler/tasks/{id}/run`, every task type) runs as the scheduler's own runs do: an asyncio task in the scheduler's `_runs`, which `stop_scheduler` ends and records as stopped at the end of the lifespan, also when the background tasks are off. Starlette's background task, which ran it before, runs after the answer, and uvicorn waits for it at its stop without a limit: a copy of days would have held the stop of the supervisor.
- **One copy, restore or change of the settings at a time**, a lock in memory. A copy that finds one running ends at once as a success, "Skipped: the copy started at <time> UTC is still running", so that the runs of a task during a first copy that takes days raise no alert. Run now, the restores, saving and forgetting the settings answer 409 then; Run now and the restores also when nothing is set up.
- **Restores**, for administrators:
  - `GET /api/v1/offsite/snapshots`: `restic snapshots --json --no-lock`, newest first, each with its kind (`configuration`, `data`) by its tag, paths, size and files.
  - `POST /api/v1/offsite/restore-configuration {snapshot_id}`: within the request, the snapshot's archive dumped into TMPDIR, checked as an upload is and stored in `/data/backups` as `offsite_<the snapshot's time in UTC>.tar.gz` (`backup.router.store_backup`, `publish_backup_file` with that time); it is restored there by the regular restore with its checks and its copy of the database.
  - `POST /api/v1/offsite/restore-files {snapshot_id, pool, path?}`: `restic restore <id>[:<path>] --target <pool's mount point>/restored-<UTC time>`, in the background, into a new folder (755) that this request makes and that is refused (409) when it exists, on a pool that is mounted; a folder that cannot be made answers 400 with the reason. `GET /api/v1/offsite/status` reports it, and its result is written to the status file. Nothing is overwritten. A restore that fails removes its folder when nothing came into it; one that a stop of the supervisor ends keeps it, as its record names it.
  - `DELETE /api/v1/offsite/settings` (Forget this target) removes the settings, the secrets and the state, their copies kept as `.bad` and the staged files of a write that a stop interrupted (`.<name>.<random>.tmp`), since a damaged or staged secrets file holds the password too; the copies stay where they are. A settings, secrets or state file that fails validation is logged with the fields and why, never their values.
- **Roles**: `supervisor/src/offsite/router.py` joins `_ADMIN_ONLY` of `main.py` and requires an administrator itself too; `supervisor/tests/test_authz.py` lists its routes.
- **The web UI**: the section Off-device copy of System > Backup & Restore (`webui/src/routes/system/tabs/OffsiteCopy.svelte`, texts in `catalog/offsite.ts`): the target (A disk or An S3-compatible store), the folders to copy (a checkbox per managed pool's mount point, by default all of them, and folders below a pool through a path field), the password twice with its warning, the retention and the check's share, Save and test, Forget this target; the state with Run now, the last copy and restore and Refresh, which reads it again (no polling, ADR-0006); "No scheduled task: copies run only on Run now" with a button that adds a daily `offsite_copy` task at 03:00; the snapshots with Restore configuration and Restore files (a pool and an optional folder). The Scheduler tab offers the type as Off-device Copy.
- **The local stand-in** (`scripts/standin/run_supervisor.py`) runs the fake restic of `supervisor/tests/fake_restic.py`, which the backend tests use as well (with restic's locks and exit status 3), puts the targets below its state directory and has no system disk: one filesystem holds all of it. The test stack has no restic and its pools share the filesystem of its data volume, so `webui/tests/offsite.spec.ts` runs its main flow on the stand-in only.
- **The device check**: `scripts/dev/scenario.sh offsite`, with a source folder and a disk target in a folder of the pool, refuses to start on a device that has a copy set up or a task of the Scheduler that copies, and leaves none. The API has no route that cancels a copy or a restore: one that outlives the check's waits makes its clean-up fail, and the final comparison reports what is left.
- A second review of the version that the device ran then led to the UTS namespace of each restic, the check without a cache, the refusal of a disk target whose disks cannot be found and the partitions of md and device-mapper devices, the account of what restic reports of vanished files, the refusal of Delete Volume and the removal of staged files by Forget.
- A review in a fresh context (ADR-0017) of the first version led to the held folders and the refusal of the Storage page, the locks, the rule for exit status 3, the comparison of whole disks, the cache of the check, `--host unos`, Run now of a task as a task of the scheduler, the 400 for a folder that cannot be made, the removal of a restore's empty folder and of the `.bad` files, the logs without values, the archive let go after its step, and the device check's refusal of a task that copies.
- Tests: `supervisor/tests/test_offsite.py`, `test_state_files.py`, `test_authz.py`, `test_standin.py`, `test_deploy_scripts.py`, `test_dev_scenarios.py`, `test_pool_persistence.py` and `test_volumes.py` (the refusals of the Storage page), `test_scheduler_validation.py` and `test_backup_restore.py` (whose clients wait for the runs that Run now starts); `webui/tests/offsite.spec.ts`, `scheduler.spec.ts`, `mobile-layout.spec.ts`.

## Consequences

- The supervisor image grows by restic (about 30 MB), and its build on the device runs apt-get once more for that layer: the owner is told before that deploy, and its SD MiB are measured.
- A forgotten repository password makes every copy useless, and UNOS cannot show it. A copy on a disk that shares a filesystem with a source does not survive that disk; the page and the answer say so, and it is what lets the dev device, with one disk, be checked.
- Only one target; SFTP, REST, a second target and a change of the password are later entries. A restore of the whole installation from the copy alone (a new device: install UNOS, enter the target and the password, restore the configuration, then the files) works through these routes, step by step.
- Runs and restores write to the system disk only the status file, the Scheduler's record and a restored configuration archive; the pack files of restic go to TMPDIR, and its cache for s3 to `/tmp`, where it takes RAM up to the tmpfs's 2 GiB together with the backups and restores that run meanwhile.
- While a copy or a restore runs, the disks it uses cannot be unmounted, from the Storage page or with a plain `umount` on the host: a copy of days blocks the unmount of its pools for days, and a disk that must go has to wait for the copy's end or a stop of the supervisor.
- The check of an s3 store downloads its share of the data on every run: 2 % checked daily is about 60 % of the repository a month, which a store that bills downloads, such as AWS S3, bills (`docs/USER_GUIDE.md`).
- The state on the page is as fresh as its last Refresh.
- The checks open the target's folder without following symbolic links, but restic opens it again by its path: a disk of its own, which the page's hint names, is the target to choose, not a folder that others can change.
- Forget this target leaves the Scheduler's `offsite_copy` tasks, whose runs then fail and are alerted until a target is set up again.

## Considered options

- btrfs send/receive: it needs btrfs on the target, and gives neither encryption nor a cloud store.
- rsync: no encryption and no versions. rclone sync: no versions; it may become a back end of restic later.
- A run that makes a missing repository: an unmounted disk would get a new repository on its mount point, on the SD card.
