# ADR-0422: Off-device copies also go to a restic REST server over HTTPS and to an SFTP server through the host's ssh, with a key pair of UNOS and the host key pinned at the first test

## Context

ADR-0337 left two targets of the copy repository for `backup.off-device-copies-over-sftp`: a restic REST server and SFTP, which "needs ssh in the supervisor image, key management and the pinning of host keys". The supervisor image has no ssh: `supervisor/Dockerfile` installs restic alone, without recommended packages. A new apt package there is a new image layer that the dev device builds and writes on its SD card, which the batch's rule allows only when the feature cannot be done safely without it. The host, a Debian or Ubuntu system, has openssh-client (priority standard; the dev device has it). The owner delegated the decision, asking above all that it be safe.

## Decision

- **Two more kinds** of `supervisor/src/offsite/service.py`, with the rest of ADR-0337 unchanged for them (one copy repository, Save tests it, the copy's steps, the check and the restore test, the restores, the locks, the timeouts, the status file):
  - `rest`: `endpoint` (`https://` only, the host and port: restic sends the server's password with every request), `prefix` (the folders on the server), `username` (no `:`), `tls` and the secret `rest_password`. `RESTIC_REPOSITORY` is `rest:https://<host>:<port>/[<prefix>/]`; the user and password go only into restic's environment, `RESTIC_REST_USERNAME` and `RESTIC_REST_PASSWORD` (restic 0.17 and later), never into the URL or an argument. `tls`: `system` (the system's roots), `ca` (a CA certificate in PEM that the administrator pastes, at most 64 KiB, which must parse), or `fingerprint`: the request names the SHA-256 fingerprint of the server's own certificate (hexadecimal, colons allowed), Save reads the certificate in a TLS handshake that sends nothing else, refuses one with another fingerprint (400 naming both) and stores the certificate in the settings (`certificate`, `certificate_sha256`). For `ca` and `fingerprint`, restic gets the certificate as `--cacert`, its only root, from a file of mode 0600 in a new folder of TMPDIR (the tmpfs, mode 0700) made for each restic command and removed after it. Before restic runs, Save and each run connect to the server as for an S3 store (`probe_store`, 10 seconds): with the system's roots, with the CA certificate (OpenSSL's partial chains allowed, as Go takes a root), or, for `fingerprint`, comparing the certificate's fingerprint with the pinned one, so that a changed certificate fails the run at the step settings with both fingerprints, and checking what Go checks of a root that is the server's own certificate (`certificate_problem`): its validity period and a subject alternative name for the host. An edit with the same endpoint and user keeps the stored password.
  - `sftp`: `host` (a host name or an IP address, stored without brackets), `port` (22), `username` (the login: letters, digits, `.`, `_`, `-`, not starting with `-` or `.`), `path` (the folder on the server: absolute, or below the login's home folder; parts of letters, digits, `.`, `_`, `+`, `-`, without `..` or `~`) and `host_key`. `RESTIC_REPOSITORY` is `sftp://<user>@<host>:<port>/<path>` (an absolute path gives `//`, restic's form).
- **SFTP runs the host's ssh, not one in the image.** restic reaches an SFTP server only through the program of `-o sftp.command`, which it starts itself. That program is `/usr/bin/ssh` of the host, started through `host.program_on_host` (`supervisor/src/host.py`) as `/usr/bin/env -i /usr/bin/ssh ...`, without restic's environment, which holds the repository's password: `nsenter --target 1 --mount --net --`, the host's mount namespace for the program and its libraries and its network namespace for its resolver and routes (a resolv.conf of the host can name systemd-resolved's 127.0.0.53), nothing else; nsenter execs ssh without a fork of its own. The files that ssh reads are in the container's TMPDIR, which `host.container_path` names through `/proc/<the supervisor's PID>/root` (with `pid: host` the PID is the host's). `ssh` joins `OPTIONAL_HOST_TOOLS` with its package `openssh-client`: `deploy/install.sh` does not install it, and Save of an SFTP target refuses a host without `/usr/bin/ssh` or `/usr/bin/env` with 400 naming the package.
- **ssh's argv is fixed** (`supervisor/src/offsite/ssh.py`): `-F /dev/null` (neither ~/.ssh/config nor /etc/ssh/ssh_config), `BatchMode=yes`, public keys only (`PreferredAuthentications=publickey`, `PasswordAuthentication=no`, `KbdInteractiveAuthentication=no`, `IdentitiesOnly=yes`, `IdentityAgent=none`), no forwarding or local command (`ForwardAgent=no`, `ForwardX11=no`, `ClearAllForwardings=yes`, `PermitLocalCommand=no`), no shared connection (`ControlMaster=no`, `ControlPath=none`), the host key only in the command's own file under `HostKeyAlias=unos-copy-target` (`GlobalKnownHostsFile=/dev/null`, `UpdateHostKeys=no`, `CheckHostIP=no`), `ConnectTimeout=10`, `ServerAliveInterval=15` and `ServerAliveCountMax=4`, `LogLevel=ERROR`, then `-p <port> -l <user> -s -- <host> sftp`. restic splits the command at spaces without a shell: every word must be one of letters, digits and `_./:=,@+-`, or the command is not built. The host, port, user, folder and pinned key are checked at Save and again before each run (`_checked`): a settings file edited by hand fails the run at the step settings before ssh runs. No password reaches any command line.
- **The key pair of UNOS.** `POST /api/v1/offsite/sftp-key` (administrators, 409 while something runs) makes an Ed25519 key pair with `cryptography` (already a runtime dependency) and stores its private key, in OpenSSH's format without a passphrase, as `sftp_private_key` in `/data/offsite_secrets.json` (mode 0600), the copy's other secrets' file; it replaces the one before, and the audit log gets `settings_changed` with the new key's fingerprint. `GET /api/v1/offsite/settings` answers the public key (`sftp_public_key`, with the comment `unos-off-device-copy`), never the private key, which reaches ssh only as a file of mode 0600 in the command's folder of TMPDIR, there for the whole restic command (a first copy can take days) and, after a crash of the supervisor, until the container's restart empties the tmpfs. Save of an SFTP target without a key pair answers 400. Forget this target removes it with the other secrets.
- **The host key is pinned at the first test.** When no key is pinned for the target's host and port, or the request sets `trust_new_host_key`, Save's `restic cat config` runs ssh with `StrictHostKeyChecking=accept-new` and an empty known_hosts file; the key that ssh wrote there is read back, and every later command, the `init` of the same Save included, runs with `StrictHostKeyChecking=yes`, that key and `HostKeyAlgorithms` of its type. The settings keep it (`host_key`, `<type> <base64>`), and the answer gives its fingerprint (`host_key_fingerprint`, `SHA256:...` as `ssh-keygen -l` prints it). A request's `host_key` is ignored. An optional `host_key_fingerprint` of the request is compared, at a first test, after `cat config` and before `init`: a server that shows another key is refused with both fingerprints and nothing written, and at a first test a server in the middle learns nothing, since `cat config` writes nothing and an SSH public-key signature is bound to its session. Another key later fails every run (restic's "Host key verification failed", at the step unlock), and a Save of the same server answers 400 with the pinned fingerprint and what to do; a Save with `trust_new_host_key` pins the new key only with the request's `host_key_fingerprint` of it (400 without one: a changed key is what a server in the middle shows), and the audit entry names `host_key` as changed. A fingerprint given while a pin is kept is compared with the pin before restic runs. A server that drops the pinned key's type fails as a changed key does ("no matching host key type found"), with the same answer.
- **No probe for SFTP**: ssh gives up after its ConnectTimeout, and restic opens the back end once, without the retries that made the probe of S3 stores necessary. ssh runs in a process group of its own, which restic gives it: the end of restic, also at its timeout, closes ssh's standard input, and the keepalives end ssh within a minute of a server that stopped answering.
- **Limits and cache**: `limit_upload_kib`, `limit_download_kib` and the cache in TMPDIR apply to s3, rest and sftp, the kinds over the network (ADR-0337 had them for s3, then the only one).
- **The web UI** (`webui/src/routes/system/tabs/OffsiteCopy.svelte`, `catalog/offsite.ts`): A restic REST server and An SFTP server among the kinds; for REST the address, folders, user, password and the certificate's check with its fingerprint or CA certificate; for SFTP the key pair (Make a key pair, the public key to copy, Make a new key pair after a confirmation), the host, port, login and folder, the optional fingerprint, and once pinned the pinned fingerprint with "trust its new key at this test".
- **The fake restic** (`supervisor/tests/fake_restic.py`) plays both servers for the backend tests and the stand-in: a REST server with its credentials and certificate, and an SFTP server reached only through `sftp.command`, whose argv it checks, with its host key, known_hosts as ssh keeps it and `authorized_keys`.
- **The device check** is not host-level: nothing on the host changes (ssh reads, its files are in the container's tmpfs). Its steps, in the entry's notes, run the real restic and the host's ssh against a REST server of `scripts/dev/restic-rest-server.py` and a second sshd of the host, both on the device's LAN address and on a folder of the pool, without the owner's second NAS.
- A review in a fresh context (ADR-0017) led to the fingerprint that trusting a new host key needs, the comparison of a fingerprint with a kept pin before restic runs, the hint for a dropped key type, `env -i`, the validity and names of a pinned certificate, the check of `/usr/bin/ssh` itself, and the tests of the CA mode against a local TLS server.
- Tests: `supervisor/tests/test_offsite_targets.py`, `test_offsite.py`, `test_restic_rest_server.py`, `test_authz.py`; `webui/tests/offsite.spec.ts`.

## Consequences

- No image layer and no new package: the copy over SFTP needs the host's openssh-client, which the host's own updates keep current, and fails Save with the package's name on a host without it.
- ssh runs as root in the host's mount and network namespaces: a flaw of the ssh client that a hostile server could use would be a flaw on the host. ssh in the privileged container would be no smaller a risk; the fixed options leave the server no agent, forwarding or command of the client to use.
- The first test trusts the key that the server shows, unless its fingerprint is typed; the page shows the pinned fingerprint to compare. A changed key is trusted only with its fingerprint.
- A REST server's pinned certificate makes a renewed certificate fail the copies until its new fingerprint is saved, and restic refuses a certificate that does not name the address entered. A REST server over plain HTTP is refused.
- restic and ssh meet a real REST or SFTP server first in the device check: the backend tests and the stand-in run the fake.

## Considered options

- openssh-client in the supervisor image: an apt layer of several MB (ssh with libfido2, libcbor, Kerberos and libedit) on the dev device's SD card, and ssh's security updates tied to rebuilds of the image; the host's ssh does the same job without either.
- The REST server's credentials in the URL of `RESTIC_REPOSITORY`: restic prints locations in its messages; the environment variables keep them out of every URL.
- `--insecure-tls` with a fingerprint checked by the supervisor beforehand: restic's own connections would then be unchecked, and a server in the middle would get the REST password.
- `ssh-keyscan` before the first test: a second connection, and keys of every type pinned; accept-new pins the one key that ssh negotiated in the connection that it tests.
