# ADR-0443: The in-app updater backs up and rolls back the database through SQLite's backup API, and installs only through a release installer that is not decided yet

## Context

Install Update and Rollback of System > Updates started nothing (ADR-0173): FastAPI's BackgroundTasks ran `asyncio.create_task` in a worker thread, and the updater ran git and `docker compose` in a checkout that the supervisor's container does not have. Its backup copied `unos.db` with `shutil.copy2` into the container's writable layer, without the commits still in `unos.db-wal`, and its rollback copied that file back beside the live log, which SQLite then reads through (ADR-0306). An interrupted update stayed "downloading" for good, and the download's progress rewrote `update_state.json` for every 8 KiB. Two choices that make an install work are settled by no ADR: where a release's images come from while GHCR has none (ADR-0050 proposes it; the workflow that would publish them is off, ADR-0230, and building them on the device writes hundreds of MB to its SD card, ADR-0214), and how the supervisor replaces its own container, since the process that runs the update is in one of the containers it replaces (entry `system.in-app-updater`).

## Decision

- **The steps the ADRs settle run in `supervisor/src/updates/updater.py`.** An update gets the release's images, then backs up the database, switches to the release and waits for it to answer, in that order (ADR-0050: images first, so that a release that cannot be had changes nothing; the backup right before the switch). The health check asks every 3 seconds for up to 300 seconds, update.sh's pause and `UNOS_HEALTH_TIMEOUT` default (ADR-0049), each check cut off at that deadline; getting the images may take up to an hour and each switch up to 700 seconds (the supervisor's 680 seconds to report healthy, `deploy/docker-compose.yml`), after which the step fails (ADR-0021). An update needs a known installed version older than the release (a build after the release's tag is not), so that it can name the version to return to. A switch that fails, or a release that does not answer in time, is rolled back at once: the backup's database is put back and the version before is started again, and the update ends failed with `rolled_back` true and its error naming the rollback. A rollback that fails too says so and keeps `can_rollback`, so Rollback can be tried again. Rollback by hand does the same with the newest backup and waits for the version before to answer; it is offered (`can_rollback`) and run only while the newest backup is of the update to the version that runs, so that after `update.sh` installed another version it does not put back an older database.
- **The backup** is `copy_database` of `supervisor/src/backup/router.py` (SQLite's backup API, with the commits still in `unos.db-wal`, switched back to the rollback journal), checked with `_verify_database`, with `backup_info.json` (the version it belongs to), in a folder `in-app-<UTC time>` of `UNOS_UPDATE_BACKUP_DIR`, renamed into place when complete, mode 700 like the folder. The newest 3 are kept. `deploy/docker-compose.yml` mounts the host's `/var/lib/unos/backups`, the setting's default and the folder of update.sh's backups, at the same path, so that a backup outlives the supervisor's container.
- **The rollback's database** goes back through the open database with the restore's `_replace_database`, after `_verify_database` and `_verify_page_size`, under `smb_lock` and followed by the restore's post-restore step (`_after_database_restore`: the tables, SMB and the iSCSI targets, ADR-0138), as a restore of a backup does: the live file stays in the write-ahead log, every connection reads the backup's content afterwards, and the supervisor that runs follows it also when the version before does not start. A backup that is missing or fails the checks fails the rollback before anything changes. A restore of a backup (`POST /backup/restore`) is refused with 409 while an update or rollback runs, and an update while a restore runs.
- **The release installer** (`supervisor/src/updates/installer.py`) is the seam of the open choices: `fetch_release`, `switch_to`, `healthy` and `switch_back`, and `unavailable_reason`. The supervisor's own is `Undecided`, whose reason names the two choices and update.sh; with it, `POST /updates/install`, `POST /updates/rollback` and turning the automatic install on answer 409 with that reason, and `GET /updates/progress` gives it as `install_unavailable`. The backend tests fill the seam with a fake. Nothing of the old path stays: the source tarball's download, its checksum asset, git, `docker compose` in the container, the copy of `/etc/unos`, `UNOS_INSTALL_DIR` and `POST /updates/reset` are removed (ADR-0207).
- **Jobs.** `start_install` and `start_rollback` check and start a job without awaiting in between, as an asyncio task on the event loop, so two requests cannot both start one. The progress is written once a step (checking, downloading, backing_up, installing, verifying, rollback, completed or failed) and carries `action` (update or rollback), `version` and `rolled_back`; `restarting` is gone. At every start the lifespan marks an update or rollback that a stop interrupted as failed, keeping its backup and `can_rollback`. The events socket sends administrators `{"type": "update", "data": <progress>}` at each step once one ran since the start, and when a change of the settings moves the next automatic look (ADR-0363's pattern), and the power schedule keeps counting a running one as a job (ADR-0407).
- **The automatic install** (`automatic_install_loop`, started in the lifespan, ADR-0043) looks every 60 seconds whether `next_automatic_check` has come: then it sets the next one an interval later, asks for the latest stable release and installs it when it is newer, as Install Update does. Turning it on, or changing its interval, sets the next look one interval later; off, there is none. The time is kept in the progress file, so a NAS that restarts more often than its interval still installs. The settings are `auto_install` and `check_interval_hours` (1 to 168) alone: `auto_check`, `include_prereleases` and `github_repo`, which nothing read, are removed.
- **System > Updates** (`webui/src/routes/system/tabs/UpdateTab.svelte`, `webui/src/lib/components/system/updates/`) shows Install Update (the tab's primary button, asked first with what it does; stable releases only), the last update with its steps from the events socket, Rollback (asked first: the database returns to the backup), the history and the automatic install only where `install_unavailable` is null, after the version card, since they load on their own (ADR-0430), with a skeleton until the updater answered. Elsewhere, as on every NAS today, it shows what ADR-0234 gave it, the update script, with the server's reason folded under "Why not from here". This ends ADR-0234's "until system.in-app-updater".
- Tests: `supervisor/tests/test_update_install.py` (the backup with the log's commits and its mount, the rollback through the open database and its post-restore step, the order of the steps, each failure, deadline and rollback, the refusals and two requests at once, the writes once a step, the interrupted update at a start, the automatic install and its loop), `test_lifespan.py` (the loop), `test_ws_auth.py` (`TestTheUpdateOnTheEventsSocket`), `test_updates.py`, `webui/tests/updates.spec.ts` and the view of `mobile-layout.spec.ts`.

## Consequences

- No NAS installs a release from the web UI until the owner decides the two choices and an installer fills the seam; until then `deploy/update.sh` stays the way to update (ADR-0049), and `system.in-app-updater` stays open.
- A rollback puts back the database of the backup: what changed after it, a user or a share made after the update, is lost, as the confirmation says. The startup reconcile of the version before repairs the host from that database (ADR-0306).
- The backups take the database's size three times on the host's disk, beside update.sh's, until a newer in-app backup replaces the oldest.
- ADR-0306's consequence that the in-app updater's copies of `unos.db` do not handle the write-ahead log yet no longer holds.
- The orchestration assumes that the process that runs it outlives the switch; an installer that restarts the supervisor in the middle has to hand the job over, which the open choice of the container's replacement settles.

## Considered options

- The backups on the data volume: no compose change, but the setting `UNOS_UPDATE_BACKUP_DIR` is a host path (ADR-0419) and update.sh keeps its backups in the same folder.
- A rollback that only starts the previous images, as update.sh's does: the database of a release that failed its health check, and its changes since the update, would stay.
